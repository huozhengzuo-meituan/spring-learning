Redis 与 Kafka 速查

缓存是可重建的副本

先明确允许陈旧多久，再选TTL与失效策略。提交后删除缓存仍可能遇到并发旧值回填；TTL是边界的一部分。数据库写失败不能让缓存先表现为成功。

docker compose exec redis redis-cli SET course:task:1 '{"title":"learn"}' EX 30
docker compose exec redis redis-cli TTL course:task:1
docker compose exec redis redis-cli GET course:task:1
docker compose exec redis redis-cli DEL course:task:1
风险方向
穿透：不存在数据校验、短空值缓存、Bloom filter
击穿：热点失效合并回源、限并发、预热
雪崩：批量失效或停机TTL抖动、回源限流、明确降级
锁过期后旧持有者继续写token释放只防误删；保护外部资源还需fencing等机制

每个投递保证都有范围

机制边界
相同key通常同分区；不是全局有序，扩分区影响映射
acks=all结合min.insync.replicas；单节点无副本容灾
幂等producer处理传输重试，不替代跨请求业务幂等
先DB后offset故障窗口会重投；同事务去重保护副作用
Outbox本地业务与待发记录原子；发送成功未标记会再发
DLT隔离毒消息，仍要告警、修复、受控重放

沿eventId查证据

outbox提交 → 发布future成功 → topic/partition/offset → group分配 → 消费异常 → 业务提交 → offset前移。lag下降不等于业务成功，丢弃消息也会让lag下降。

事件考虑eventId、type、schemaVersion、aggregateId、occurredAt。新增可选字段比改名与改变语义更易兼容；先部署兼容消费者。JSON能解析不能证明金额单位、时区和状态含义正确。
