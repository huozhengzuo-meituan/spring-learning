拆开 Spring Boot 自动配置

用条件报告解释一个自动配置为何生效或未生效。

约 25 分钟先修：06Java 21 · Boot 4.1
从你的前端经验出发

自动配置类似框架根据已安装插件和配置组装运行环境，但它有可查看的条件，不是无法理解的黑盒。

本课服务于同一个目标：独立交付并排查可靠的业务后端。实验入口：examples/hello-api。标注为教学片段或设计实验的代码需要按题目补入，不代表示例已实现该功能。

从启动入口到条件装配

@SpringBootApplication 集成配置声明、自动配置启用和组件扫描等常用能力。你自己的控制器通常通过组件扫描进入容器，框架提供的基础设施则可能来自自动配置。两条路径相关却不相同：包扫描范围错误可能导致控制器不见了，而排除某个自动配置通常不会替你找到业务类。

自动配置会观察 classpath、已有 Bean、配置属性等条件。例如存在数据库依赖不代表连接地址一定正确；存在某个类也不代表所有自动配置都会启用。一个常用原则是用户明确提供 Bean 后，相关默认实现可能退让，但具体哪些条件退让必须读对应配置，不能概括成所有自定义 Bean 都能替代全部默认设置。

原始资料：Spring Boot 自动配置。

用条件报告建立证据

给应用传入 --debug 可以看到条件评估报告。报告中的 positive matches 表示条件匹配，negative matches 表示某项条件没满足。后者大量存在是正常的：你的 MVC 服务本来就不需要所有消息队列和响应式数据库配置。目标不是把所有项目变成 positive，而是找出与你遇到的问题直接相关的条目。

下面仍启动现有 hello-api，不需要增加代码。首先从 pom 确认使用 MVC starter，然后在报告中查找 MVC 和 WebServer 相关条目。把一个条件的输入和结果记录下来，你就能从“Boot 大概帮我做了”变为“因为某类存在且缺少自定义 Bean，所以默认方案建立”。

./mvnw -f examples/hello-api/pom.xml spring-boot:run \
  -Dspring-boot.run.arguments=--debug
# 第二个终端验证服务仍能处理请求
curl -i http://localhost:8081/api/tasks

自定义时缩小改动范围

想调整端口应先找配置属性，而不是重写服务器工厂；想增加 MVC 拦截器可寻找对应扩展接口，而不是复制整套 MVC 配置。过早使用 @EnableWebMvc 可能改变 Boot 的默认装配方式，导致原有行为消失。排除自动配置也应有明确原因和验证，不把它当成通用消错按钮。

常见陷阱是把启动类放在业务包的下层，导致同级包不在默认扫描范围；另一个是手动构建 JSON mapper 后漏掉框架模块。Boot 4 使用 Jackson 3，主映射器与定制接口都应看当前文档。保留最小复现：一次只改一个条件，用启动报告和 API 响应验证因果，再决定是否保留变更。

合上笔记，先判断

条件报告里大量 negative matches 表示什么？
查看判断依据

正确答案：很多能力未启用。很多自动配置本来就不适用于当前应用。必须结合相关条件判断，不能只数 negative 项。

把知识变成操作

解释 hello-api 中一个自动配置的命中条件。

  1. 以 --debug 启动 hello-api。
  2. 找到一个 MVC 或容器相关 positive 条目和一个不相关 negative 条目。
  3. 写下每个条目的条件输入，并确认 GET /api/tasks 仍返回200。
验收信号

至少解释一项命中、一项未命中，同时证明服务正常。

做完再看：参考答案与排错线索

答案应包含因果而非复制名称，例如“当前为Servlet Web应用、相关类在classpath，因此MVC配置候选命中；缺少某消息中间件类，对应配置未启用”。具体类名以本次报告为准。
