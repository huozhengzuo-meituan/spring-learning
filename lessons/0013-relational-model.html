用 PostgreSQL 建立关系模型

让数据库约束独立维护数据有效性，而非只依赖服务代码。

从你的前端经验出发

前端对象可以临时不完整；数据库是持久化事实来源，要在并发和多入口下保持约束。

本课服务于同一个目标：独立交付并排查可靠的业务后端。实验入口：独立 PostgreSQL / psql 实验。标注为教学片段或设计实验的代码需要按题目补入，不代表示例已实现该功能。

从业务不变量反推表结构

先写业务规则，再选择字段。任务必须属于一个合法用户，标题不能为空，同一用户的业务编号不可重复；这些规则分别对应外键、非空或检查约束、唯一约束。主键标识一行，业务唯一键表达另一种不重复要求，二者通常不是同一回事。字符串“001”与数字1也不应仅为方便就混用。

金额使用精确数值或最小货币单位，时间需明确是否是时间点。PostgreSQL的timestamptz存储时间点并按会话时区显示，不保存输入时的原始时区名称；若业务需要地区时区规则，还应保存对应标识。NULL表示缺失或未知，判断使用IS NULL，不能用等号与NULL比较。

运行一个可回滚的独立模型

在根目录执行 docker compose up -d postgres，随后执行 docker compose exec postgres psql -U learning -d learning 进入专用学习数据库。下列实验全在事务内创建临时命名的教学表，并在最后回滚，不依赖task-service真实表名。你可以把SQL整体保存后执行，也可逐句运行观察结果。正式服务结构仍由Flyway管理，不手工修改线上表。

第一张表维护用户，第二张表维护任务。外键确保不能引用不存在的用户，检查约束保证状态只能是枚举集合。注意检查约束并不能替代NOT NULL，因为NULL参与检查时可能得到未知而不被拒绝。语义明确的约束能让SQL客户端、批处理和HTTP接口共享同一底线。

BEGIN;
CREATE TABLE lab_users (id bigint PRIMARY KEY, email text NOT NULL UNIQUE);
CREATE TABLE lab_tasks (
  id bigint PRIMARY KEY,
  owner_id bigint NOT NULL REFERENCES lab_users(id),
  title text NOT NULL CHECK (length(trim(title)) > 0),
  status text NOT NULL CHECK (status IN ('TODO','DONE')),
  created_at timestamptz NOT NULL DEFAULT now()
);
INSERT INTO lab_users VALUES (1, 'learner@example.test');
INSERT INTO lab_tasks(id, owner_id, title, status) VALUES (1,1,'学SQL','TODO');
SELECT t.title,u.email FROM lab_tasks t JOIN lab_users u ON u.id=t.owner_id;
ROLLBACK;

关系数据库共享思想，方言并不相同

PostgreSQL和MySQL都支持关系模型、索引和事务，但自增写法、JSON操作、大小写行为、时间类型、错误码及默认隔离级别有差异。MySQL还要明确使用支持事务的引擎。课程主线统一PostgreSQL，跨库时重新跑真实数据库测试，不以H2兼容模式作为完整迁移证明。

常见陷阱是把全部业务结构放进JSON列，这确实灵活，却可能失去清晰的约束与查询路径。稳定、需要筛选或关联的核心字段适合关系列；变化快的附属内容再考虑JSON。扩展练习可以为任务加优先级，但先说明值域和默认值，再决定类型和约束，而不是照着接口字段机械建表。

数据库约束错误应在应用层转换为可理解的结果，但不要因害怕出现错误就删除约束。应用预检查能改善用户体验，数据库约束处理并发竞争，两者应一起存在。模型评审时用两个同时提交的请求作为例子，更容易发现只靠单线程推理遗漏的不变量。
