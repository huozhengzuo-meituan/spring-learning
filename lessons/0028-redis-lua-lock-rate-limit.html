Redis 原子操作、Lua、锁与限流

用原子脚本保证计数与过期一起完成，并说明租约锁的边界。

约 30 分钟先修：第25课：TTL / 第27课：缓存保护Java 21 · Boot 4.1
从你的前端经验出发

浏览器中一次函数同步执行不代表远端多条请求原子；客户端先 GET 再 SET 会让多个请求互相覆盖。

本课服务于同一个目标：独立交付并排查可靠的业务后端。实验入口：独立 Redis CLI。标注为教学片段或设计实验的代码需要按题目补入，不代表示例已实现该功能。

原子操作保护的是什么

INCR 将一个键的读取和递增放在 Redis 内部完成；多条客户端命令依旧可以被其他客户端穿插。Lua 脚本在服务器上执行，可以把有限的一组操作组合起来，执行期间不会插入其他普通命令。这个优势也意味着长脚本会拖慢整个实例。脚本不是数据库回滚事务：脚本运行时已经成功的写入，不会因为后续命令报错自动撤销。先检查参数，再做写入，且所有 key 通过 KEYS 显式传递。

一个可运行的固定窗口限流器

下面最多允许同一键在首次请求后的十秒内通过三次。计数与设置过期放在同一个脚本，避免 INCR 后客户端崩溃导致计数永不过期。调用 EVAL 的 1 代表一个 key，随后是窗口毫秒与限额。它适合演示原子性；固定窗口在边界可能短时放过接近两倍限额，因此更平滑的要求需令牌桶或滑动窗口。

docker compose exec redis redis-cli EVAL 'local n=redis.call("INCR",KEYS[1]); if n==1 then redis.call("PEXPIRE",KEYS[1],ARGV[1]); end; if n<=tonumber(ARGV[2]) then return 1 else return 0 end' 1 course:limit:user7 10000 3
# 在10秒内执行4次：前三次1，第四次0。
docker compose exec redis redis-cli PTTL course:limit:user7

租约锁不能替代业务约束

单实例获取锁可用 SET key 随机token NX PX 5000；释放必须比较 token 相同再删除，不能直接 DEL。否则持有者 A 暂停超过五秒，B 已拿到新锁，A 恢复后会误删 B 的锁。即使正确释放，过期的 A 仍可能继续操作外部数据库，锁本身阻止不了它。对库存、金额等正确性要求高的写入，仍要数据库条件更新、唯一约束，必要时由下游拒绝旧 fencing token。复制故障切换也可能丢失刚写的锁。

检查工作负载和失败路径

限流必须决定 Redis 不可用时是放行还是拒绝：公开写接口通常需要更保守的保护，非关键读取可能使用本地预算降级。不要把每个随机请求ID用作限流key，那会失去用户维度聚合并制造大量键。Cluster 中多key原子脚本要求键落在同一哈希槽；不要为了跨实体原子性把所有键都塞进同一个槽。这里的脚本没有写入真实任务，练习结束可让学习键自然过期。把“谁被限制、多久、最多多少、失败怎么处理”写成接口约定。

固定窗口计数会把被拒绝的请求也计入当前窗口，但不会延长窗口寿命，这一点应写进预期。检查返回值时区分允许、拒绝和脚本执行失败，不要把网络异常当作普通拒绝静默吞掉。为了让演练可重复，使用新的课程键，避免上一次计数影响本次结果。

验证限流和安全释放，并模拟旧持有者恢复。

  1. 十秒内调用脚本四次，记录返回值。
  2. SET course:lock tokenB NX PX 30000。
  3. EVAL 比较GET值是否等于ARGV[1]，相同才DEL，传入tokenA。
  4. GET course:lock，确认仍是tokenB；再用tokenB释放。
