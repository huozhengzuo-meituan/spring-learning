本课服务于同一个目标：独立交付并排查可靠的业务后端。实验入口：examples/hello-api。标注为教学片段或设计实验的代码需要按题目补入，不代表示例已实现该功能。

三个边界各自负责什么

JSON 解析先检查输入能否转换为 Java 类型；Bean Validation 再检查字段是否满足约束；服务层检查跨字段与当前业务状态；数据库最终维护唯一性和引用完整性。这几层不是重复劳动。例如标题为空可在入口立即拒绝，而“同一用户不能创建重复项目名”需要数据库唯一约束抵御并发，单纯先查询再插入并不可靠。

请求 DTO 明确允许客户端提交的字段。客户端不能通过额外发送 ownerId 或 admin 字段夺取权限，服务必须从已认证身份得出操作者。响应 DTO 则控制返回内容。若直接用实体接收表单，模型中后来新增的字段可能被自动绑定，造成超出预期的修改范围。

原始资料：Spring MVC Validation。

声明规则，同时验证规则会执行

Boot 4 示例使用 jakarta.validation 包，并显式引入 validation starter。@NotBlank 同时拒绝 null、空字符串和只有空白的字符串；@Size 约束长度，但通常不会单独拒绝 null，所以不能把它当作必填。嵌套对象需要级联校验的 @Valid。仅在 record 上写注解不会让每个 new 都自动抛错，校验必须由MVC或显式Validator触发。

下面是教学 DTO，演示规则组合，不要求覆盖项目现有类型。控制器的 @Valid @RequestBody 告诉 MVC 在参数绑定后触发校验。字段长度的技术定义和产品对字数的理解可能不同，尤其面对emoji；产品要求复杂时需定义自定义规则和相应测试，而不是假定字符数等于用户感知字数。

import jakarta.validation.Valid;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.Size;

record CreateTaskRequest(
    @NotBlank @Size(max = 120) String title) {}

失败反馈必须可以修正

校验错误应指向可操作字段与稳定的错误代码，让前端能提示用户修正。不要把完整请求体或密码写入错误日志。服务层不能因为MVC已经校验就放弃关键不变量，因为同一用例也可能被消息消费者、定时任务或其他内部入口调用。

最常见的假成功是只测合法输入。至少测试空字段、空白字段、边界长度、超出长度、类型不匹配和无效JSON。它们可能走不同异常处理路径，因此同样是400也要保持可理解的响应。请求不合法时数据库和内存状态都应不变，验证失败只返回400却已经保存数据，仍然是错误实现。

curl -i -X POST http://localhost:8081/api/tasks \
  -H "Content-Type: application/json" --data '{"title":" "}'
curl -i -X POST http://localhost:8081/api/tasks \
  -H "Content-Type: application/json" --data '{}'
curl -i -X POST http://localhost:8081/api/tasks \
  -H "Content-Type: application/json" --data '{"title":'

合上笔记，先判断

只写 @Size 能否确保字段必填？
查看判断依据

正确答案：仍需非空约束。长度约束通常允许null；必填需要NotNull、NotBlank等符合字段语义的约束。

把知识变成操作

证明坏输入不会改变服务状态。

  1. 先GET任务列表，记录数量。
  2. 逐个执行本课三个坏请求，记录返回状态和字段信息。
  3. 再次GET，确认数量没增加；合法title应能正常创建。
验收信号

坏请求返回4xx且无任务新增；合法请求成功。

做完再看：参考答案与排错线索

空白和缺少title应被必填规则拒绝，无效JSON在解析阶段失败。两个阶段都不应调用保存逻辑。若坏请求竟成功，检查validation starter、@Valid位置及字段注解，而不是只改前端校验。
