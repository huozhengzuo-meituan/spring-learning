Lesson 12 / 48 · 02 · HTTP 与可测试 API

JUnit、MockMvc 与测试边界

为业务规则、HTTP合同和外部集成选择恰当测试层。

约 30 分钟先修：11Java 21 · Boot 4.1
从你的前端经验出发

组件单测不能证明整个页面可用；同样，普通Java测试、MVC测试和真实数据库测试证明的是不同范围。

本课服务于同一个目标：独立交付并排查可靠的业务后端。实验入口：examples/hello-api。标注为教学片段或设计实验的代码需要按题目补入，不代表示例已实现该功能。

先问这条测试要证明什么

纯单元测试直接构造对象，适合状态转换、计算和边界规则；它无需启动Spring，反馈快。MVC切片测试关注路由、参数绑定、校验和响应；业务协作者可以替换。应用集成测试加载更完整的上下文，适合检查装配、事务和外部系统边界。层级更大不代表每条测试价值更高，重复验证getter不会弥补关键失败场景缺失。

MockMvc 通过MVC基础设施处理模拟请求，通常无需真实HTTP端口。它可以证明请求经过绑定和控制器后得到预期响应，但无法证明反向代理、TLS、真实网络超时或容器部署配置。端到端测试需要额外经过真实服务端口。报告结果时应说清楚测到了哪一层，不用“全都测过”代替范围。

原始资料：Spring MockMvc。

写能发现行为回归的断言

好的断言描述业务后果：空白标题不能保存；创建返回201且资源可查询；不存在的任务返回404。只断言方法被调用一次而不看结果，常会错过字段错误或副作用。测试数据应独立，不能依赖上一条测试恰好创建了某个id，否则顺序变化和并行执行都会暴露脆弱性。

下面演示MockMvc断言风格，项目测试已有对应依赖时可参考扩展。Boot 4的测试模块和部分注解包路径已迁移，优先使用项目现有import和当前官方API。替换Bean使用Framework的 @MockitoBean 等现代支持，不要从旧文章复制已淘汰的测试注解。

// 教学测试方法，放在已配置 MockMvc 的测试类中
mockMvc.perform(post("/api/tasks")
    .contentType("application/json")
    .content("{\"title\":\" \"}"))
  .andExpect(status().isBadRequest());

// 根目录运行现有示例的测试
// ./mvnw -f examples/hello-api/pom.xml test

原始资料：Spring Boot Testing。

失败注入比快乐路径更有价值

至少为关键用例保留一个拒绝输入或依赖失败的测试。修改规则后先看测试是否能失败，再恢复正确实现；如果怎么改它都绿，断言可能没有覆盖要害。不要为了通过测试去捕获所有异常并返回默认值，这会把测试的信号消掉。

Mock 是局部替身，不能证明真实数据库方言、约束、锁和事务行为。后续用Testcontainers补齐数据库证据。运行结果也要区分“通过”“未执行”“因缺少Docker跳过”。构建退出码为零却跳过了集成测试，不等于外部系统行为已经验证。现在先用短反馈循环建立正确断言，再扩展环境。

原始资料：Spring Boot Testing。

查看判断依据

正确答案：公网证书的可用。MockMvc通常不经过真实网络和部署入口，无法证明TLS与代理配置。

把知识变成操作

读懂并运行 hello-api 的现有测试。

  1. 执行 ./mvnw -f examples/hello-api/pom.xml test。
  2. 找一条成功测试和一条失败输入测试，写出各自证明的行为。
  3. 设计一个新增边界案例及预期结果；若实施修改，再运行同样命令。
