Lesson 17 / 48 · 03 · 数据库与事务

用事务保护完整业务结果

通过失败实验确认多次数据库修改一起成功或一起撤销。

约 30 分钟先修：16Java 21 · Boot 4.1
从你的前端经验出发

多个await不自动成为一个原子业务；后端也不能把“先后调用成功过”当成一致性保证。

本课服务于同一个目标：独立交付并排查可靠的业务后端。实验入口：独立 PostgreSQL / psql 实验；examples/task-service。标注为教学片段或设计实验的代码需要按题目补入，不代表示例已实现该功能。

原子性保护一个业务单位

转账需要扣减甲账户并增加乙账户，任务变更需要更新任务并记录待发送事件。如果第二步失败而第一步已经永久提交，系统留下半成品。数据库事务把相关操作组成一个提交单位，失败时回滚。隔离性处理并发可见性，持久性处理提交后的保存保证，一致性则仍需正确业务规则和约束共同维护。

事务不能覆盖任意外部副作用。数据库回滚不会自动撤销已经发出的邮件、HTTP请求或Kafka消息。本项目把任务与outbox_events写在同一数据库事务，后续再发送消息，就是为了把“必须同时落库”的状态先绑定起来。事务中直接发送外部通知，仍然有数据库提交与通知成功之间的间隙。

原始资料：Spring @Transactional。

用故障而不是快乐路径证明回滚

以下实验在psql同一个会话中完成。临时表只存在于当前会话，初始余额各100。第一次事务扣减后主动回滚，应恢复总额与各账户余额；第二次正常提交后余额变成70与130。先预测结果再执行，比背诵ACID更容易形成可以迁移到代码的判断。

如果SQL发生约束错误，PostgreSQL事务会进入失败状态，需要回滚或回到保存点。不要把某条SQL失败后继续执行的结果，与成功提交混为一谈。把每次检查放在事务结束之后，还可避免只看到自己事务中的未提交数据而误判成功。

CREATE TEMP TABLE lab_accounts(id integer PRIMARY KEY, balance integer NOT NULL CHECK(balance>=0));
INSERT INTO lab_accounts VALUES (1,100),(2,100);
BEGIN;
UPDATE lab_accounts SET balance=balance-30 WHERE id=1;
ROLLBACK;
SELECT * FROM lab_accounts ORDER BY id;
BEGIN;
UPDATE lab_accounts SET balance=balance-30 WHERE id=1;
UPDATE lab_accounts SET balance=balance+30 WHERE id=2;
COMMIT;
SELECT * FROM lab_accounts ORDER BY id;

原始资料：PostgreSQL Transactions。

Spring回滚规则需要明确

@Transactional通常放在公开业务用例方法上，让一次用例包含的仓库操作共享事务。默认情况下RuntimeException和Error触发回滚，受检异常默认不会；可通过rollbackFor或全局策略显式调整。不能只看异常名字是否含Error就猜测行为，必须看类型及实际配置。catch住异常后正常返回，也可能使事务继续提交。

readOnly=true主要表达只读意图并给底层优化机会，不是跨所有驱动都可靠的写入防火墙。事务应尽量短，避免用户交互和慢网络占用连接。对照TaskService.create与transition，找出任务写入和outbox写入为什么属于同一个用例，并思考第二步异常是否真的穿过事务边界。

原始资料：PostgreSQL Transactions。
