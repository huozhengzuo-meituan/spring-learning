Lesson 30 / 48 · 06 · Kafka 与事件一致性

Kafka：日志、分区、key 与顺序

创建双分区主题，观察同key顺序和不同消费组的独立进度。

约 30 分钟先修：第21课：真实依赖测试边界 / SETUP.md：按需启动KafkaJava 21 · Boot 4.1
从你的前端经验出发

前端事件总线通常随页面消失；Kafka把事件写成持久日志，让订阅者按自己的进度重放。

本课服务于同一个目标：独立交付并排查可靠的业务后端。实验入口：独立 Kafka CLI；使用根 compose.yaml 的 kafka 服务。标注为教学片段或设计实验的代码需要按题目补入，不代表示例已实现该功能。

消息不是消费后立刻消失

topic 是逻辑事件集合，partition 是有序追加日志，offset 是该分区的位置。消费者读取后日志仍按保留策略存在，其他消费组可以独立读取。顺序边界是分区，不是整个topic。记录key通常决定路由，同一业务实体使用相同key有利于保持该实体的事件顺序；多个生产者并发仍需设计业务版本和冲突规则。Kafka 4主线使用KRaft管理元数据，本课程不再把ZooKeeper当作Kafka启动前置。

运行双分区实验

根Compose启动kafka后，官方镜像中的工具位于 /opt/kafka/bin。以下创建课程独立主题，副本数1仅为单节点本地演示。创建完成后生产者进入交互输入；输入两行后用Ctrl-C退出，再执行消费者命令。相同key的两条事件应出现在同一分区且offset递增；打印分区与offset才是在验证顺序，不能只看时间戳。

docker compose up -d kafka
docker compose exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --create --if-not-exists --topic course.tasks --partitions 2 --replication-factor 1
docker compose exec kafka /opt/kafka/bin/kafka-console-producer.sh --bootstrap-server localhost:9092 --topic course.tasks --property parse.key=true --property key.separator=: 
# 交互输入：
42:created
42:completed
# 退出生产者后：
docker compose exec kafka /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic course.tasks --from-beginning --max-messages 2 --property print.key=true --property print.partition=true --property print.offset=true

增加分区不是透明的顺序升级

对默认按key哈希分区的逻辑，增加分区数可能改变key映射；历史记录留在旧分区，新记录进入新分区，不能再依赖它们位于同一条日志。扩容前要设计迁移、停写窗口或消费者版本约束。一个消费组中某分区通常只由一个消费者实例负责，因此实例多于分区时会有闲置。热点key也可能让一个分区承担大部分流量，单纯加机器不能自动解决。分区数是并行度、顺序与运维成本之间的选择。

给事件定义含义

“用户要求完成任务”是命令，“任务已经完成”是事实事件；把两者混用会让消费者无法判断是否需要再次执行业务。事件要有eventId、实体ID、发生时间、类型和schema版本；只发送消费者真正需要的数据。保留期决定故障后最多能重放多久，压缩主题适合保留key最新状态，但不是所有业务事件审计的等价替代。本课只要求认识日志边界，后面会把投递、处理和数据库副作用分开证明。

一手阅读：Kafka Quick Start；Kafka 分区与协议。带着本课实验的输出阅读；有任何不清楚的步骤，可以直接把命令和结果发给学习助手继续追问。

分区中的offset是记录位置，可能不连续地出现在你看到的业务消息中，例如事务控制记录和日志清理会影响可见性。不能把两个业务消息offset之差简单当成准确待处理业务条数。事件保留策略与消费组进度独立，长时间离线消费者可能失去可重放的历史。

合上笔记，先判断

Kafka 原生日志顺序直接保证的范围是什么？
查看判断依据

正确答案：单个分区内部。offset是分区内的位置；不同分区没有天然全局顺序，消费速度也可不同。

把知识变成操作

向双分区主题发送两个任务的状态事件，并观察路由。

  1. 为本次练习创建一个新的双分区主题（例如 course.tasks.exercise1；已存在时换后缀），把生产者和消费者的 --topic 同步改成此主题，发送42:created、43:created、42:completed、43:completed。
  2. 将消费者改为 --max-messages 4，输出key、partition与offset；本次新主题应只有这4条记录。
  3. 按key整理输出，确认实体内顺序。
  4. 解释为何不能根据跨分区输出先后判断业务全局顺序。
验收信号

同一key路由相同且offset递增；不同key可能同分区也可能不同，不能预设恰好均分。

做完再看：参考答案与排错线索

分区数量固定且默认key路由下同key同分区；并行消费的跨分区显示顺序不构成全局事件顺序。
