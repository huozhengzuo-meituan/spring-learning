Spring Integration、调度与分布式任务

区分定时触发、消息管道和可靠作业执行，避免多实例重复副作用。

约 30 分钟先修：第44课：批处理 / 第28课：锁边界Java 21 · Boot 4.1
从你的前端经验出发

浏览器setInterval只是触发回调；服务端@Scheduled也只是调度入口，不自动提供集群唯一执行与可靠重试。

本课服务于同一个目标：独立交付并排查可靠的业务后端。实验入口：独立分布式作业设计；调度片段为增量。标注为教学片段或设计实验的代码需要按题目补入，不代表示例已实现该功能。

触发时间不是业务保证

@Scheduled可按固定延迟、固定速率或cron触发；fixedDelay围绕上次结束后的间隔，fixedRate围绕固定时间节奏，实际并发仍取决于调度器和执行方式。时区和夏令时会影响日历调度，业务日期要显式定义。部署两个应用实例通常就有两个本地定时器，不能假设只执行一次。进程停机错过的触发是否补跑、一次执行过长是否重叠，都必须在作业语义里约定。

把定时器变成轻量入口

下面是教学触发片段，仅唤醒扫描逻辑；真正任务由持久表记录，按业务主键和运行日期唯一约束领取。不同实例竞争领取时，通过数据库原子状态迁移或有界租约决定责任。即使租约超时后旧执行者恢复，也要靠幂等业务写或版本约束避免重复副作用。不要把所有工作放进一个永不返回的调度方法，也不要在线程池排队无限多相同扫描任务。

@Scheduled(fixedDelayString = "${course.scan-delay:5000}")
void scanDueWork() {
    // 只领取有限批次，不在这里假定集群全局唯一。
    // 唯一键可用(job_name, business_date, entity_id)。
    runner.claimAndExecuteBoundedBatch();
}
// cron示例：@Scheduled(cron="0 0 2 * * *", zone="Asia/Shanghai")

Integration 用管道连接异构系统

Spring Integration提供Message、Channel、Endpoint及转换器、路由器、适配器，适合把文件、数据库、HTTP等集成为消息流。消息包含payload和headers，DirectChannel的调用链可在同一线程，QueueChannel引入队列与轮询消费者。选择异步通道就引入排队、失败传播与事务边界变化；一个普通内存队列不会在重启后自动恢复。Poller负责按节奏读取可轮询源，必须设批量、超时和错误处理，避免下游慢时继续无界灌入。

选工具时看恢复与规模

简单进程内维护工作可用@Scheduled；有checkpoint的大量数据处理用Batch；异构消息路由用Integration；需要持久触发与集群调度可评估Quartz等专门调度器或平台任务能力。框架名称不是互斥选择：调度器可以触发Batch，Integration可以接入输入，但业务幂等仍独立存在。实验从两个实例同时扫描一项过期任务开始，记录领取者、尝试号、完成状态与失败原因，证明重复触发不会重复关闭任务或发送通知。

作业状态表需要监测卡住的RUNNING记录和持续失败的RETRY记录。运维重试按钮应生成审计记录，而不是直接把所有状态清零。即便选择成熟调度平台，也应验证它重新投递一次任务时，数据库更新和外部通知是否仍满足业务不变量。

查看判断依据

正确答案：各自执行定时器。本地调度默认每实例独立执行，集群唯一责任需要额外协调，业务仍应幂等。

把知识变成操作

设计多实例的过期任务提醒。

  1. 定义唯一业务键：提醒类型、任务ID、业务日期。
  2. 画出PENDING到RUNNING到DONE或RETRY的状态迁移。
  3. 模拟两个实例竞争领取及执行者崩溃。
  4. 指出调度器、Batch、Integration在该需求中的可选职责。
验收信号

重复触发不重复发送，崩溃任务可重领；消息或外部通知仍使用稳定幂等标识。
