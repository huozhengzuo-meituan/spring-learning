Lesson 37 / 48 · 07 · 可靠性与运行时

Actuator：指标、日志与 trace

从一次慢请求出发，用三类证据定位发生在哪一层。

约 30 分钟先修：基础HTTP与安全 / 第34课：outboxJava 21 · Boot 4.1
从你的前端经验出发

前端DevTools看一条请求；后端需要把HTTP、数据库、缓存、Kafka之间的执行关系拼起来。

本课服务于同一个目标：独立交付并排查可靠的业务后端。实验入口：examples/task-service + 管理端点；追踪后端为后续增量。标注为教学片段或设计实验的代码需要按题目补入，不代表示例已实现该功能。

三种证据各自回答问题

指标适合回答总体发生了多少、多久、是否偏离目标；日志记录具体事件和上下文；trace把一次操作跨多个服务的调用串起来。只堆日志会让容量与检索成本失控，只看平均值会掩盖少量极慢请求。Spring Boot Actuator提供管理能力，Micrometer Observation统一很多观测入口。没有接入追踪导出器与后端时，添加Actuator不等于已经获得完整分布式trace。对课堂环境先看健康与现有指标，再逐步连接采集系统。

暴露端点也是安全设计

管理端点要限制暴露和访问范围。健康端点可供探针使用，但配置、堆转储和环境等信息不能随意公开。下面是教学配置：是否允许匿名访问还由Spring Security配置决定。使用真实路由模板作为指标标签，例如/api/tasks/{id}，不要使用每个任务的实际ID，否则时间序列数快速增长。用户ID、eventId和traceId放日志或trace上下文，不放无限取值的指标标签。

management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics
  endpoint:
    health:
      show-details: when_authorized
# 开发环境观察已启用端点：
# curl -i http://localhost:8080/actuator/health
# 非公开端点需按项目README提供认证。

为业务补上最少观测点

自动HTTP与JVM指标看得到服务外壳，还需要业务观测：任务创建成功数、版本冲突数、outbox最老待发年龄、消费重复数。日志至少区分info事件与error失败，保留异常堆栈而不是只打印“失败了”；删除请求正文中的密码、令牌和不必要个人数据。通过MDC或框架追踪上下文把同一次操作关联起来；切线程和消息边界时需要传播上下文，不会因为字段名叫traceId就自动联通。

用证据缩小范围

假设接口p95升高：先看错误率与吞吐是否同时变化，再查数据库连接等待、SQL耗时、Redis延迟及Kafka发布积压；随后按慢trace定位跨度，再用对应日志解释原因。每个猜想应给出可反驳证据，例如“CPU低而连接等待高”更像下游或池饱和而非算力不足。监控必须能区分依赖不可用与应用自身死锁，这也关系到第46课探针设计。最后保留一份真实请求、时间窗口、指标与原因链，而非漂亮却无法行动的看板。

一手阅读：Spring Boot 可观测性；Spring Boot 指标。遇到不明白的输出、时序或取舍，请把你的推理发给学习助手继续追问。

日志量也有预算。对高频成功请求采用合适采样，错误日志防止同一异常在每一层重复打印。请求标识应在入口产生或严格验证来源，避免用户输入任意换行破坏结构化日志。排查结束后保留低成本常驻指标，清理临时高噪声诊断。

哪一项更适合成为HTTP指标标签？
查看判断依据

正确答案：固定路由模板。固定路由模板具有有界基数。令牌敏感，随机ID使时间序列数量失控。

把知识变成操作

为一次创建任务请求写观测证据清单。

  1. 启动task-service，检查health实际返回。
  2. 按README认证查看已配置的其他管理端点，不假定全部公开。
  3. 选三项指标、两条结构化日志字段与一个trace关联字段。
  4. 构造一次版本冲突，说明它应如何被观察且避免记录敏感凭据。
