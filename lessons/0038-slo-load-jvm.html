Lesson 38 / 48 · 07 · 可靠性与运行时

SLO、压测与 JVM 诊断

制定可测服务目标，并用压测和JVM证据定位瓶颈。

约 30 分钟先修：第37课：可观测性Java 21 · Boot 4.1
从你的前端经验出发

前端性能预算约束用户等待；后端SLO同样从用户体验出发，不是把CPU使用率本身当目标。

本课服务于同一个目标：独立交付并排查可靠的业务后端。实验入口：examples/task-service + JDK21 jcmd；压测脚本为增量练习。标注为教学片段或设计实验的代码需要按题目补入，不代表示例已实现该功能。

先定义测量口径

SLI是测量指标，例如有效任务查询中在300ms内成功的比例；SLO是目标，例如滚动七天达到99.5%。这是教学目标，真实数值要根据业务与成本决定。明确分母是否包括客户端取消、鉴权失败与计划停机，否则各看板无法比较。错误预算是允许不达标的部分，用来约束发布与可靠性投入。p95不是95%的请求都刚好这个耗时，而是分位边界；平均值低不能说明长尾用户体验好。

负载模型决定结论适用范围

压测需写出数据规模、并发、请求速率、读写比例、缓存冷热、运行时间、机器规格与版本。先预热JIT，再测稳定段，最后增加负载找拐点；不要只测试所有请求都命中同一热key的快乐路径。闭环用户模型会因系统变慢而自动减少新请求，可能掩盖过载，恒定到达率模型有助于观察积压。每次只改变一项关键变量，才能把收益归因到修改。未安装压测工具时也应先写完整实验计划。

使用 JDK 自带诊断工具

在开发进程上运行jcmd -l寻找PID；命令需要与目标JVM的权限和环境相匹配。JFR记录低开销运行事件，线程栈帮助定位阻塞与竞争。堆转储可能暂停进程并包含敏感业务数据，不作为第一步随手操作。下面是本地诊断命令，先确认PID指向课堂进程。

jcmd -l
# 将12345换成task-service对应PID，记录30秒JFR：
jcmd 12345 JFR.start name=course settings=profile duration=30s filename=course-load.jfr
jcmd 12345 Thread.print
jcmd 12345 GC.heap_info
# 记录文件后用Java Mission Control等工具分析热点与等待。

把排队看成信号

并发数近似等于吞吐乘平均在系统内停留时间，只在适用的稳定条件下作估算：100 QPS、平均0.2秒约意味着20个并发在途请求。如果连接池只有10个且每次请求长时间占用连接，线程再多也不会消除排队。CPU高看计算热点，CPU低且延迟高看锁、连接等待与远端调用。诊断输出应包含假设、证据、单项修改和复测结果；“换更大机器”可以暂时扩容，但不能替代对瓶颈与容量上限的认识。

一手阅读：k6 API 压测；JDK21 jcmd。遇到不明白的输出、时序或取舍，请把你的推理发给学习助手继续追问。

不要把本机短时基准直接外推为生产容量。容器限额、数据库网络距离、索引规模、并发写入和缓存冷启动都会改变结论。压测报告应明确哪些条件未覆盖，并给出下一轮验证计划；诚实的容量区间比一个没有条件的最高吞吐数字更能指导部署。

正确答案：定位长尾请求源。少数极慢请求会伤害用户体验并扩大排队，应结合trace、连接等待和JVM事件定位。

把知识变成操作

为任务查询写可复现压测方案并做一次本地诊断。

  1. 记录Java版本、数据量、请求比例、缓存状态与资源限制。
  2. 选择正常流量和接近容量两档，写出停止条件。
  3. 若有压测工具运行短时负载；同时采集一次JFR。
  4. 把p95、错误率、吞吐、CPU和连接等待放在同一时间窗口比较。
