Lesson 18 / 48 · 03 · 数据库与事务

代理、自调用、传播与隔离

准确判断事务从哪里开始，遇到嵌套调用如何组合。

约 30 分钟先修：17Java 21 · Boot 4.1
从你的前端经验出发

装饰器写在方法上不等于每一次调用都被拦截；Spring事务的常见实现依赖调用经过代理对象。

本课服务于同一个目标：独立交付并排查可靠的业务后端。实验入口：examples/task-service。标注为教学片段或设计实验的代码需要按题目补入，不代表示例已实现该功能。

先画调用路径再看注解

默认代理模式中，调用者先进入代理，代理开启或加入事务，再调用目标方法。目标对象内部用this调用另一个方法，通常不会重新经过代理，因此内部方法上的事务属性不因该调用而生效。如果外层本来已有事务，内部代码仍在那笔事务中执行；“自调用无效”不意味着内部永远没有事务，而是不会按内部注解新建或改变边界。

构造器、初始化方法和手动new对象也不应被假定享有完整代理增强。解决自调用问题通常是把独立事务用例拆到另一个Bean，或用TransactionTemplate明确包围需要的代码。不要为了绕过代理限制引入隐藏的自我注入，让调用图更难理解。

传播解决嵌套边界，隔离解决并发观察

REQUIRED在已有事务时加入，否则新建，是常见默认行为。REQUIRES_NEW建立独立事务，外层会被挂起；内部提交后，外层随后回滚并不会撤销已独立提交的内部结果。它也可能需要额外数据库连接，多个外层事务同时等待内部连接会耗尽连接池。NESTED通常借助保存点，是否支持取决于事务管理器和资源。

隔离级别是另一维度。PostgreSQL默认Read Committed下，不同语句可看到不同的已提交快照；Repeatable Read提供更稳定快照，但不等同于自动防止全部业务并发异常。Serializable可能拒绝无法串行化的事务，应用需要有界重试整个事务。MySQL默认配置常不同，不能按名称猜测完全相同的实现行为。

// 教学反例：inner 的 REQUIRES_NEW 不会因 this 调用而生效
@Transactional
public void outer() {
  this.inner();
}
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void inner() {
  // 若需独立事务，移到另一个注入Bean再由outer调用
}

// psql中确认当前会话隔离级别
// SHOW transaction_isolation;

rollback-only也是需要处理的状态

内部REQUIRED调用与外层共享同一物理事务。如果内部把事务标记为rollback-only，外层即使捕获异常并继续执行，也不能保证最后提交成功，可能收到UnexpectedRollbackException。这不是框架“明明没异常却回滚”，而是先前的失败已经影响共同事务。正确做法是明确用例的失败合同，而非在外层无限catch。

本项目private append没有自己的事务注解，但从public事务方法调用时仍使用现有事务，这是有意的结构。与自调用反例比较，可避免误以为每个数据库方法都必须再写一次注解。练习中分别写出逻辑方法边界和物理事务数量，能把两层区分开才算掌握传播。

原始资料：PostgreSQL 隔离级别。

外层有事务并this调用内部方法时，内部通常怎样？
查看判断依据

正确答案：沿用外层事务。内部注解不会被这次自调用重新拦截，但已有外层事务仍覆盖执行过程。

把知识变成操作

分析三个调用场景的物理事务数量。

  1. 场景A：无事务调用者→代理outer REQUIRED→this.inner REQUIRES_NEW。
  2. 场景B：无事务调用者→代理outer REQUIRED→另一个Bean的inner REQUIRES_NEW。
  3. 场景C：outer REQUIRED→另一个Bean的inner REQUIRED，内部标记rollback-only。
验收信号

A一笔事务；B两笔独立事务；C一笔共同事务且最终不能正常提交。

做完再看：参考答案与排错线索

A内部注解没有经过代理，仍是一笔；B外层挂起、内部独立提交或回滚；C共享物理事务，外层捕获异常不能取消rollback-only。实际是否支持某传播方式需看事务管理器。
