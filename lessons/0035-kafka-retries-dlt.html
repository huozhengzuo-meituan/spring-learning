Kafka 重试、DLT 与毒消息

让可恢复错误重试、永久坏消息可调查，并保持明确的顺序契约。

约 30 分钟先修：第32课：offset / 第33课：幂等消费Java 21 · Boot 4.1
从你的前端经验出发

前端错误边界隔离局部崩溃；消费者也不能让一条坏记录无限堵住全部事件，又悄悄把失败吞掉。

本课服务于同一个目标：独立交付并排查可靠的业务后端。实验入口：独立重试设计；配置片段是未并入项目的增量练习。标注为教学片段或设计实验的代码需要按题目补入，不代表示例已实现该功能。

先分类再决定重试

网络短暂不可达、外部限流等可能恢复；字段格式不对、违反不可变业务规则等通常不会靠等待自动修好。反序列化失败甚至发生在监听方法之前，需要相应反序列化与容器错误处理。限制重试次数与总时间，记录原因和原始位置。把所有异常都无穷重试，会让坏记录变成持续阻塞；把所有异常都忽略，会让业务永久缺失。DLT是死信主题，用于保留失败证据与后续处理，不是自动修复设施。

阻塞与非阻塞重试的取舍

阻塞重试可暂停当前分区进展，便于维持顺序，但会增加lag。非阻塞重试把消息转移到重试主题，主主题继续处理，吞吐更灵活，却可能让后续状态先被处理。Spring Kafka的重试主题机制有适用边界，不能默认和容器事务自由组合。若任务状态严格按版本推进，先定义乱序和缺口处理，再选择重试模式。不要为了消除lag数字，把本应停止的业务序列盲目发到DLT后继续。

一个错误处理器的意图

下面是教学配置片段，使用现有KafkaTemplate并需要在独立练习配置类中提供相关import。DLT一般应有足够分区以承接原始分区，生产环境应显式创建topic、ACL与保留策略；不要依赖自动建topic碰运气。DefaultErrorHandler配合recoverer在重试耗尽后投递失败记录；必须同时考虑DLT发布失败如何阻止错误地确认原记录。

var recoverer = new DeadLetterPublishingRecoverer(kafkaTemplate);
// 首次失败后再尝试2次，每次间隔1秒；总尝试3次。
var handler = new DefaultErrorHandler(
    recoverer, new FixedBackOff(1000L, 2L));
handler.addNotRetryableExceptions(IllegalArgumentException.class);
// 将handler接入监听容器工厂；具体接线见官方当前版本文档。

重放是一项有审计的操作

DLT记录需要原topic、partition、offset、eventId、失败类型和时间，但异常文本也可能泄漏敏感数据，应控制访问。运维人员修复schema或代码后，按小批次重放，保留同eventId，并观察数据库幂等及错误率。重复失败时立即停止，不能无限在主主题与DLT之间循环。完成标准是坏消息可定位、正常消息按约定继续、告警触达且能复原影响范围。只看消费者进程还活着，不能证明它还在正确处理。

一手阅读：Spring Kafka 错误处理；非阻塞重试。遇到不明白的输出、时序或取舍，请把你的推理发给学习助手继续追问。

死信主题也要有访问权限、保留期限和容量预算。若它填满或发布失败，原消息是否提交必须明确定义并测试。恢复人员应能根据事件标识找到业务状态；没有关联标识的错误文本，即便保存了很多，也难以判断哪些用户真正受到影响。

正确答案：实体事件会乱序。失败记录延后处理时，主主题后续事件可能先完成；需要业务版本、缺口策略或选择阻塞重试。

把知识变成操作

给四种失败写重试矩阵。

  1. 列出连接超时、临时限流、缺少必填字段、数据库唯一键冲突。
  2. 填写是否重试、最大次数、退避、是否DLT。
  3. 说明唯一键冲突在重复事件与真实业务冲突两种场景的区别。
  4. 制定DLT小批重放与停止条件。
验收信号

永久格式错误不会无限重试；重复事件可按幂等成功处理；业务冲突有单独判定。
