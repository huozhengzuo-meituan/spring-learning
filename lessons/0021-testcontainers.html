Lesson 21 / 48 · 03 · 数据库与事务

用 Testcontainers 获得真实数据库证据

区分H2测试与PostgreSQL集成测试，并运行真实数据库约束实验。

约 35 分钟先修：20Java 21 · Boot 4.1
从你的前端经验出发

接口mock可以验证前端分支，却不能证明服务真的兼容上游；数据库替身也有相同局限。

本课服务于同一个目标：独立交付并排查可靠的业务后端。实验入口：examples/task-service：独立JUnit/Testcontainers教学增量。标注为教学片段或设计实验的代码需要按题目补入，不代表示例已实现该功能。

真实依赖回答替身回答不了的问题

H2适合无需外部服务的快速反馈，但PostgreSQL的UUID、时间类型、DDL、锁等待和SQL语法可能不同。Testcontainers在测试时启动指定镜像的真实服务，分配端口并在结束后清理，让测试更接近生产协议。它仍不是生产环境的完整复制：数据规模、网络拓扑、资源限制和多节点故障还需另外验证。

测试必须能说明究竟连到哪里。数据库容器启动成功但应用仍使用H2，属于无效证据。可验证数据库产品名、版本和连接URL，或者使用PostgreSQL专属行为作为断言。没有Docker时应明确报告该测试未运行，不把跳过包装成通过；需要这层证据的CI应把环境不可用视作失败。

原始资料：Testcontainers PostgreSQL Module。

明确依赖与生命周期

Testcontainers 2使用更明确的模块名称，PostgreSQL模块为testcontainers-postgresql，包为org.testcontainers.postgresql。数据库驱动也要存在，容器库不会自动替你加上所有驱动。Spring Boot的@ServiceConnection可从容器推导连接信息，需要spring-boot-testcontainers测试依赖。

下面是独立JUnit实验的完整类，可作为学习增量添加到task-service测试目录；需先加入Testcontainers PostgreSQL测试依赖，版本遵循父POM的依赖管理。它不加载Spring，只验证真实PostgreSQL事务行为。已有同类测试时直接运行现有测试，避免重复创建。命名与依赖以项目最终README为准。

package dev.learning.tasks;

import java.sql.DriverManager;
import org.junit.jupiter.api.Test;
import org.testcontainers.postgresql.PostgreSQLContainer;
import static org.junit.jupiter.api.Assertions.assertEquals;

class PostgreSqlRollbackTest {
  @Test void rollbackRemovesInsertedRow() throws Exception {
    try (var pg = new PostgreSQLContainer("postgres:17.11-alpine3.23")) {
      pg.start();
      try (var c = DriverManager.getConnection(pg.getJdbcUrl(), pg.getUsername(), pg.getPassword());
           var sql = c.createStatement()) {
        assertEquals("PostgreSQL", c.getMetaData().getDatabaseProductName());
        sql.execute("create table proof(id integer primary key)");
        c.setAutoCommit(false);
        sql.executeUpdate("insert into proof values(1)");
        c.rollback();
        try (var result = sql.executeQuery("select count(*) from proof")) {
          result.next();
          assertEquals(0, result.getInt(1));
        }
      }
    }
  }
}

原始资料：Spring Boot Testcontainers。

从数据库实验扩展到应用事务测试

以上测试证明数据库回滚，却不能证明TaskService真的把两个写入放进同一事务。下一步应加载应用、指向容器数据库、触发用例并在第二步注入失败，随后在独立查询中验证tasks和outbox_events都没有部分结果。不要让测试自身的@Transactional掩盖服务遗漏的事务边界。

容器与Spring上下文都有生命周期，跨测试缓存上下文时，过早停止静态容器可能让后续测试持有失效连接。容器作为Spring测试Bean管理通常更容易保持生命周期一致。每条测试隔离数据，避免依赖执行顺序；镜像版本固定，升级时把迁移和锁行为重新纳入验证。

容器镜像下载失败属于环境或网络问题，测试断言失败才指向被测行为，二者应分开记录。CI可以预拉取镜像并复用下载缓存，但不能复用脏业务数据而破坏测试隔离。资源清理也应有界，异常退出后检查残留容器，不随意删除其他项目的容器。

原始资料：Spring Boot Testcontainers。

把知识变成操作

运行真实PostgreSQL回滚测试，或明确记录环境缺口。

  1. 确认 docker info 成功；检查task-service是否已有等价Testcontainers测试与运行命令。
  2. 若没有，在测试范围添加org.testcontainers:testcontainers-postgresql并创建本课完整测试类；PostgreSQL驱动项目已提供。
  3. 运行 ./mvnw -f examples/task-service/pom.xml -Dtest=PostgreSqlRollbackTest test；记录测试是否实际执行。
验收信号

真实数据库产品名为PostgreSQL，插入回滚后count=0；缺少Docker必须报告未验证。

做完再看：参考答案与排错线索
