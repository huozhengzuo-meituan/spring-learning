Java 虚拟线程与异步上下文

运行虚拟线程，并说明它为什么不能扩大数据库容量。

约 30 分钟先修：第38课：JVM诊断 / 第39课：并发预算Java 21 · Boot 4.1
从你的前端经验出发

你熟悉async/await让I/O等待不占满执行线程；虚拟线程让Java用顺序代码表达大量等待，但仍要控制资源。

本课服务于同一个目标：独立交付并排查可靠的业务后端。实验入口：独立 Java21 jshell；Boot配置为可选实验。标注为教学片段或设计实验的代码需要按题目补入，不代表示例已实现该功能。

便宜的等待不是更快的计算

Java21的虚拟线程适合大量阻塞I/O任务，使等待不必总占用同等数量的操作系统线程。CPU密集计算仍受核心数量约束；数据库连接、下游QPS、内存和文件句柄也不会因此变多。每个请求可以拥有虚拟线程，但不能为每个请求创建无限数据库连接。通常不把虚拟线程放进固定大小的虚拟线程池复用；需要限制外部资源时使用连接池、信号量或业务队列。应先测阻塞位置，再判断是否带来收益。

用 Java21 直接运行

在jshell中运行这段完整片段，会创建独立虚拟线程执行任务，Future.get等待结果并传播失败；try-with-resources关闭executor并等待任务结束。示例延迟模拟I/O等待，只证明调度与等待语义，不是性能基准。不要在业务中为了假装异步而立即submit后get再添加不必要切换，真实收益来自多个等待任务可并发服务。

import java.util.concurrent.*;
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    var result = executor.submit(() -> {
        Thread.sleep(100); // 模拟等待；真实代码是受控的I/O
        return "virtual=" + Thread.currentThread().isVirtual();
    });
    System.out.println(result.get());
}
// Boot配置开关：spring.threads.virtual.enabled=true

版本与线程绑定状态的陷阱

Java21中某些synchronized内的阻塞和native调用会使虚拟线程固定在载体线程上，影响扩展性；可通过JFR等证据定位，不应把后续JDK改进当成Java21已有行为。ThreadLocal在虚拟线程上仍可使用，但每线程缓存巨大对象会放大内存。Spring事务通常与当前线程绑定，跨到@Async方法不会自动继承原事务；代理自调用还可能导致@Async根本没有生效。任务失败必须被future或异常处理器观察到。

让上下文传播显式可验证

日志traceId、安全上下文、租户ID都是上下文，但传播方式与边界各不相同。不能简单复制一个ThreadLocal就声称所有异步安全；新任务可能在原请求结束后继续运行。Spring Boot当前对自动配置AsyncTaskExecutor可通过spring.task.execution.propagate-context选择观测上下文传播，自定义执行器需要相应TaskDecorator。安全身份和事务仍要按各自机制处理。测试时同时检查正常值、异常清理和下一次请求不会继承上次数据。

关闭请求或取消任务时应保留中断语义。代码捕获InterruptedException后若继续无限循环，会破坏退出预算；应终止工作或按调用约定恢复中断状态。虚拟线程演示成功只能证明基本运行，是否改善课堂服务的吞吐仍需要相同负载条件下的对照实验。
