用构造注入理解 IoC

解释对象由谁创建，并写出不依赖 Spring 容器的业务测试。

从你的前端经验出发

前端组件通过 props 接收依赖；后端业务对象也应明确声明所需协作者，而不是在方法中到处 new。

本课服务于同一个目标：独立交付并排查可靠的业务后端。实验入口：独立 jshell 实验。标注为教学片段或设计实验的代码需要按题目补入，不代表示例已实现该功能。

把创建对象的责任移出业务

控制反转的实际含义很具体：业务类声明自己需要什么，容器负责把对象组装好。创建任务的服务需要一个存储接口，却不应该在每次调用时自行创建数据库连接。构造注入把这个要求变成对象存在的前提；没有依赖就无法构造，减少“对象已创建但还没初始化”的中间状态。

Spring 的 Bean 是容器管理的对象，不是看到 new 就自动接管。你在测试中 new 一个服务完全合理，只需提供依赖；但自己 new 一个标有事务注解的服务，不会自动获得容器代理。这一区别将贯穿缓存、事务和异步课程，先把普通 Java 对象与容器增强对象分开理解。

用极小对象图验证理解

下面是独立 Java 教学代码，可以直接放进 jshell。接口隔离的是“存储任务”能力，而不是为了接口数量本身。业务服务只维护标题规则；内存替身用于观察调用。换成真实存储时，业务规则无需知道连接字符串或 SQL。给每个类都机械地创建同名接口，并不会自动获得良好设计。

迁入 Spring 后，服务可标记 @Service，存储实现可标记 @Repository，只有一个构造器时不需要额外写 @Autowired。若同类型存在多个候选 Bean，容器需要 @Qualifier 或 @Primary 等明确选择。不要用随机改 Bean 名字解决歧义，先画出你真正想注入的对象关系。

interface TaskStore { void save(String title); }
class CreateTask {
  private final TaskStore store;
  CreateTask(TaskStore store) { this.store = store; }
  void create(String title) {
    if (title.isBlank()) throw new IllegalArgumentException("blank");
    store.save(title);
  }
}
var saved = new java.util.ArrayList<String>();
var service = new CreateTask(saved::add);
service.create("学习注入");
System.out.println(saved);

原始资料：Spring @Bean 依赖声明。

依赖方向比注解数量更重要

控制器负责 HTTP 参数和响应，服务负责用例，存储负责数据访问。依赖通常从外部入口流向业务和数据接口，避免控制器互相调用或仓库去寻找 HTTP 请求。这样测试服务无需起端口，未来换数据库也不会迫使每个控制器重写。

常见陷阱是字段注入后在普通单元测试里直接 new，导致依赖为 null；另一个是循环依赖，A 构造需要 B，而 B 构造又需要 A。循环通常说明职责没分清，优先抽出共同协作或重新确定用例边界。不要先靠延迟加载隐藏它。本课交付物不是注解清单，而是一张能解释创建顺序的对象图。

好的构造器依赖应少而明确。如果一个服务要接收十几个不相关协作者，先审查它是否承担过多用例；把依赖藏进一个全局容器查询器只会把问题变得不可见。测试替身应模拟具体边界，不必复制真实数据库的全部功能。

把知识变成操作

在 jshell 运行对象图，然后用替身验证拒绝空标题。

  1. 执行本课代码，确认 saved 有一条。
  2. 执行 service.create(" ") 并观察异常。
  3. 再查看 saved.size()，判断错误输入是否触发存储。
验收信号

有效标题被保存；空白标题抛异常；列表仍只有一条。

做完再看：参考答案与排错线索

saved.size() 应为 1。服务在调用 store.save 之前拒绝空白标题。Spring 版本的唯一区别是把 CreateTask/实现注册为 Bean，由容器调用构造器；业务逻辑本身无需依赖容器 API。
