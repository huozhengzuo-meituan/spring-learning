Lesson 09 / 48 · 02 · HTTP 与可测试 API

把 REST 设计成资源合同

为任务创建、查询和状态变化选择稳定的 HTTP 语义。

约 30 分钟先修：08Java 21 · Boot 4.1
从你的前端经验出发

前端关心请求怎么调用；全栈工程师还要定义重试、安全性、缓存和错误的合同。

本课服务于同一个目标：独立交付并排查可靠的业务后端。实验入口：examples/hello-api。标注为教学片段或设计实验的代码需要按题目补入，不代表示例已实现该功能。

资源与表示先于注解

任务是资源，/api/tasks 表示集合，/api/tasks/{id} 表示单个任务。HTTP 返回的 JSON 是资源的一种表示，不应直接等于数据库表的所有字段。控制器映射负责把 method 与 path 连接到用例；业务规则仍应该留在服务层。路径名称一致比给每个动作设计一个随意缩写更容易维护。

GET 用于读取，调用者可以合理期待它不会执行可观察的业务修改。POST 常用于创建或提交命令；成功创建可返回 201 和 Location。PUT 表达指定资源的替换语义，PATCH 表达部分修改；它们的具体字段语义需写进合同。DELETE 的幂等性描述重复请求的目标状态，而不是要求每次状态码完全一样。

原始资料：HTTP 方法与状态码 RFC 9110。

幂等性与表单按钮无关

请求可在浏览器重试、代理重试或用户重新打开页面时重复。PUT 通常应设计成相同输入达到相同目标状态；POST 创建不能仅靠前端禁用按钮保证不重复。状态更新也需区分“设置为DONE”和“完成数加一”，前者容易做成幂等操作，后者天然需要额外去重或条件控制。

返回成功前应决定任务是否已经持久化、是否只是被接收。202 表达已接受但尚未完成，不适合伪装已经完成的业务。201 的 Location 应指向新资源，客户端可据此查询。为了保持教学简单，本课先观察已有 hello-api 的创建和查询；异步任务、幂等键与并发版本将在后续课程继续完善。

状态码是可编程接口的一部分

400 用于无法接受的请求，401 表示缺少或无效认证，403 表示无权执行，404 表示资源不存在，409 可表达当前资源状态造成的冲突。不要把所有错误包成 HTTP 200 再让前端猜 success 字段，这会削弱代理、监控、SDK 和重试策略的共同语义。相反，业务错误也不应全部变成500。

常见陷阱是接口返回数据库实体，后来加了内部备注或权限字段，字段就被意外公开。使用响应 DTO 明确允许暴露的字段，日期格式、分页结构和错误结构也要稳定。练习的真正产物是一段可被前后端共同检查的合同：请求、成功响应、失败响应、重复调用后果各写清一项。

原始资料：Spring MVC 请求映射。

HTTP 幂等性描述的是什么？
查看判断依据

正确答案：重复请求的效果。幂等性关注重复执行对目标资源的预期效果，不能由响应文本或耗时是否相同判断。

把知识变成操作

建立一条任务并写出它的最小 API 合同。

  1. 启动 hello-api，POST title，记录状态码、Location与返回id。
  2. 使用真实id执行GET，确认标题与创建一致。
  3. 设计“设置任务完成”和“完成数加一”的重复请求结果。
验收信号

创建后能按实际id查询；能解释两个操作为何具有不同的重复执行风险。

做完再看：参考答案与排错线索

合同例：POST /api/tasks 接收非空title，成功201并返回新资源；GET已存在id返回200，缺失返回404。设置DONE重复执行目标仍DONE；加一重复执行会再次增加，因此需要幂等键或条件更新。
