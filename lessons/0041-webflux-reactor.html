WebFlux、Reactor 与背压的边界

比较MVC与WebFlux，并正确组合非阻塞流与阻塞依赖。

约 30 分钟先修：第40课：并发模型 / 第39课：超时与隔离Java 21 · Boot 4.1
从你的前端经验出发

Promise表达一次结果，Observable表达结果序列；Mono与Flux也表达异步数据，但还要处理订阅、背压和调度。

本课服务于同一个目标：独立交付并排查可靠的业务后端。实验入口：独立架构与Reactor增量设计；不混入现有MVC项目。标注为教学片段或设计实验的代码需要按题目补入，不代表示例已实现该功能。

先识别现有依赖

WebFlux采用非阻塞模型，以少量事件循环线程服务许多等待中的请求；Spring MVC采用更直接的命令式模型，可以与虚拟线程结合。已有JDBC/JPA阻塞访问的任务服务，先用MVC通常更易理解与维护；不能因为响应返回Mono就宣称整条链路已经非阻塞。WebClient也可在MVC项目中使用，不必为了调用一个远程接口迁移整个应用。选择依据是等待特征、依赖支持、团队调试能力和实测收益。

Mono与Flux描述执行过程

Mono代表零或一个值，Flux代表零到多个值；多数冷发布者在订阅时才执行。map做同步值转换，flatMap组合返回Publisher的异步操作，flatMap并发会影响输出次序，concatMap更侧重逐项顺序。异常也是流的信号，应使用onError等策略处理，而不是在外面try/catch期待捕获稍后发生的错误。Web框架通常负责订阅HTTP处理链，业务方法里随手subscribe会使错误、生命周期和取消脱离请求。

背压并不等于无限缓存

背压让消费者表达需求量，但外部数据源不一定能减速，必要时只能有界缓冲、丢弃或失败。onBackpressureBuffer如果不限制容量会把慢消费者变成内存问题。下面是独立Reactor片段，需要相应依赖；它不是已并入task-service的完整功能。遗留阻塞调用可暂时隔离到boundedElastic，但不会因此变成真正非阻塞数据库驱动，仍要限制并发。

Mono<TaskView> result = Mono.fromCallable(() -> legacyDao.load(42L))
    .subscribeOn(Schedulers.boundedElastic()) // 隔离阻塞，保留资源预算
    .timeout(Duration.ofMillis(300));

Flux<TaskView> ordered = Flux.just(42L, 43L)
    .concatMap(id -> remoteClient.find(id)); // 逐项保持输出顺序
// 不在事件循环上调用block()或Thread.sleep()。

用可观察的测试选择模型

选一个高等待、低CPU的接口，对MVC平台线程、MVC虚拟线程和纯非阻塞链分别设计同等资源测试。记录吞吐、p95、线程、连接等待与代码复杂度。用StepVerifier可检查流的值、错误和完成信号，还应测试取消是否释放资源。ThreadLocal不是Reactor Context，跨调度线程时要正确传播观测与身份信息。不要为了课程覆盖面把MVC主项目强行混入两种服务端栈；本课首先完成模型判断，再在独立分支做小范围增量。

响应式代码中的重试通常会重新订阅上游，若上游包含副作用，可能再次执行写入。不要因为操作符名叫retry就忽略第33课的幂等要求。流完成、出错和取消都可能触发资源清理，测试应覆盖三个终止方式，并观察连接是否真正归还。

正确答案：事件循环被占用。少量事件循环线程被阻塞时会影响许多请求；应选择MVC或显式隔离遗留阻塞调用并设预算。
