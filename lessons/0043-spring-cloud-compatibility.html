Spring Cloud：Gateway、Config 与服务发现

明确Cloud组件的职责，并用官方兼容表管理Boot与Cloud版本。

约 35 分钟先修：第42课：服务边界 / 第39课：依赖保护Java 21 · Boot 4.1
从你的前端经验出发

开发代理集中路由接口；生产网关也路由请求，但还涉及认证边界、限流、超时和多实例发现。

本课服务于同一个目标：独立交付并排查可靠的业务后端。实验入口：独立Cloud架构增量；不修改主线依赖。标注为教学片段或设计实验的代码需要按题目补入，不代表示例已实现该功能。

按问题选组件

Gateway负责入口路由、过滤与跨切面策略；Config集中提供外部配置；Discovery帮助寻找服务实例；LoadBalancer选择具体实例。一个服务用固定地址和环境配置就能运行，不必先部署整套注册中心。Kubernetes已提供服务发现时也要评估是否还需要额外注册机制。配置中心不能替代密钥管理，网关认证不能替代业务服务中的资源授权。每增加一个控制组件，就增加需要监控、升级和恢复的依赖。

先查兼容表再复制依赖

本课程主线Java21、Spring Boot4.1.1。2026年9月核对的Spring Cloud官方表将2025.1.x列为Boot4.0/4.1兼容系列，其中Boot4.1支持从2025.1.2开始。后续学习时重新查表，不要把日期敏感选择永久写死。通过Cloud BOM协调组件版本，不单独混装不同代Gateway、Config、Commons。以下展示BOM结构，版本值需从当次官方兼容表或Initializr生成，未核对时不添加到现有项目。

<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>org.springframework.cloud</groupId>
      <artifactId>spring-cloud-dependencies</artifactId>
      <version>${spring-cloud.version}</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>

配置拉取也会失败

Config Client可通过spring.config.import指定配置源；加optional表示配置不可用时允许继续，若关键生产配置缺失不应默认静默启动。明确哪些配置可动态刷新、哪些必须重启，以及回滚到哪份配置版本。服务发现返回实例不代表实例此刻健康，客户端仍需要超时和失败处理。网关路由要保留请求ID，正确处理路径重写和转发头信任范围；允许用户随意控制目标URL会造成开放代理或SSRF风险。

做小而完整的链路实验

在独立增量实验里建一个网关路由到任务服务，先固定本地地址验证，再考虑发现机制。测试正常访问、后端不可达、认证失败、路径不存在四种反馈。不要向已有MVC主程序同时塞入不兼容的网关服务端栈；Gateway有不同运行模型，按当前文档选择并独立部署。配置中心失效演练要说明启动时与运行中各有什么行为。最终交付应该包含依赖树和兼容依据，而不是仅一段能编译的路由配置。

一手阅读：Spring Cloud 兼容表；Spring Cloud Gateway；Config Client。把你的实验记录和取舍理由发给学习助手，可以继续追问并获得反馈。

从当前版本生成依赖后，保存依赖树与启动验证。能下载依赖不等于兼容，能启动也不等于路由、鉴权与配置刷新全部正确。升级时先在隔离分支验证真实请求，再推进主线；不要通过关闭版本兼容校验来掩盖不匹配，否则运行时错误更难定位。
