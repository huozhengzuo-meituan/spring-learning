JPA 实体生命周期与脏检查

区分普通对象、托管实体、SQL同步与事务提交。

约 30 分钟先修：14Java 21 · Boot 4.1
从你的前端经验出发

前端状态更新通常立即修改内存；JPA还维护一层持久化上下文，内存改变与SQL发送、提交不是同一时刻。

本课服务于同一个目标：独立交付并排查可靠的业务后端。实验入口：examples/task-service；实体状态推演。标注为教学片段或设计实验的代码需要按题目补入，不代表示例已实现该功能。

实体不是JSON，也不是表本身

JPA是持久化规范，Hibernate是常用实现，Spring Data JPA再提供仓库抽象。实体表达持久化身份和状态，使用jakarta.persistence注解。为满足映射与实例化约定，实体一般使用普通类和无参构造器，不直接采用record。对外传输仍使用DTO，避免把关联关系、内部字段和懒加载行为暴露到JSON序列化。

new出来的实体还没有被持久化上下文管理；persist后成为托管状态；上下文关闭或detach后，Java对象还存在但不再受脏检查追踪。remove标记删除，实际SQL时机仍与flush相关。理解状态比记住save方法更重要，否则你很难解释为什么改了字段却没有更新数据库。

原始资料：Spring Data JPA Persisting Entities。

保存、合并与脏检查

在活动事务中读取到的托管实体，修改字段后通常由脏检查在flush时生成更新，无需每次再显式save。Spring Data save会根据实体是否为新对象决定persist或merge；merge返回托管副本，传进去的原对象并不会因此必然变成托管对象。忽略返回对象再继续修改，可能产生令人困惑的结果。

下面是教学实体片段，展示身份、版本和修改入口。它不要求替换项目现有实体。完成映射还要匹配数据库迁移，并由事务服务调用；只有实体类本身不能证明数据库操作成功。把状态改变收口到有业务名称的方法，可比公开所有setter更容易维护规则。

import jakarta.persistence.*;
@Entity
class NoteEntity {
  @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
  private Long id;
  @Version private Long version;
  @Column(nullable = false) private String title;
  protected NoteEntity() {} // 供持久化框架实例化
  NoteEntity(String title) { rename(title); }
  void rename(String title) {
    if (title == null || title.isBlank()) throw new IllegalArgumentException();
    this.title = title;
  }
}

原始资料：Jakarta Persistence 规范。

flush不等于commit

flush把持久化上下文中的改动同步为SQL，commit才最终提交事务。flush后如果事务回滚，普通事务性数据库中的修改仍应撤销。约束错误有时到flush或commit才出现，因此“save没抛异常”不能保证提交成功。生成ID也不意味着这条记录已经永久可见。

懒加载关联需要可用的持久化上下文，离开事务后访问可能报错。不要通过无条件保持会话跨整个HTTP请求来掩盖边界；更清晰的方案是在事务内完成需要的查询并映射DTO。练习先画出对象状态，再读取真实项目的服务事务和实体映射。如果项目某个路径用JDBC，也应理解它没有JPA这一层脏检查。

持久化上下文还提供同一身份对象的一致视图，同一上下文中重复读取同一个主键可能得到同一托管实例。批量处理大量实体时，这些对象占用内存；需要按批次处理与适当清理，而不能把所有记录读入一个超长事务后再逐一修改。

new为瞬态，persist后托管，修改被追踪，flush可能执行INSERT/UPDATE，rollback撤销数据库修改。Java对象字段不保证自动恢复。项目使用JPA，TaskService.transition中的tasks.flush()用于让版本更新和冲突在构建事件之前发生。
