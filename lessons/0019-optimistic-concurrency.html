乐观锁与原子条件更新

防止两个请求覆盖同一份状态，并把冲突反馈给客户端。

约 35 分钟先修：18Java 21 · Boot 4.1
从你的前端经验出发

两个浏览器标签页保存同一表单时，后提交的人可能携带旧数据；后端需要识别“我修改的还是原来那一版吗”。

本课服务于同一个目标：独立交付并排查可靠的业务后端。实验入口：独立双会话 PostgreSQL 实验；examples/task-service。标注为教学片段或设计实验的代码需要按题目补入，不代表示例已实现该功能。

丢失更新与超卖是不同表现的同类问题

两个事务都读到库存1，各自在内存里减一后写0，表面库存不为负，但已经卖出两件。任务也一样：两个标签页都读到version=3，分别提交不同状态，后写入可能覆盖前一次。只在业务代码里先查询检查，不能阻止检查与写入之间出现竞争。

乐观锁把版本加入更新条件。JPA的@Version使更新通常包含旧版本条件并递增版本，影响行数不符时抛出乐观锁异常。API同时让客户端回传它看到的版本，可更早识别过期编辑；数据库的版本条件才守住最后的并发边界。预检查不替代@Version，两者覆盖不同时间窗口。

原始资料：Spring Data JPA Locking。

把不变量写进同一条SQL

库存扣减可直接表达为UPDATE ... SET quantity=quantity-1 WHERE quantity>0。判断与修改由数据库在同一语句中完成，受影响行数为1才代表扣减成功。乐观版本更新也类似：WHERE id=? AND version=?，同时SET version=version+1。不能忽略返回0，否则客户端会以为修改成功。

以下独立实验用专门schema lab_l19，让两个psql会话共享同一行。先由会话A建表并插入，随后A更新但暂不提交，B执行相同扣减会等待；A提交后B重新判断条件，应更新0行。执行完只清理本课schema，避免影响应用表。

CREATE SCHEMA lab_l19;
CREATE TABLE lab_l19.stock(id integer PRIMARY KEY, quantity integer NOT NULL);
INSERT INTO lab_l19.stock VALUES (1,1);
-- 会话A：执行更新后暂时停住
BEGIN;
UPDATE lab_l19.stock SET quantity=quantity-1 WHERE id=1 AND quantity>0;
-- 会话B：同样执行BEGIN和UPDATE，观察等待
-- 会话A：COMMIT;
-- 会话B：等待结束，预期UPDATE 0，然后COMMIT;
-- 两边事务结束后查询：
SELECT * FROM lab_l19.stock;
-- 实验结束清理：DROP SCHEMA lab_l19 CASCADE;

原始资料：PostgreSQL 并发控制。

冲突需要可理解的恢复路径

任务修改冲突适合返回409，让前端重新读取最新状态，再让用户决定是否重新提交。不能把旧请求原封不动无限重试，因为它携带的业务意图可能已经失效。对机器可重试的短事务，可使用有限次数、退避和幂等性保护；重试范围应包含重新读取与重新计算，而不是只重复失败的SQL。

本项目TaskService.transition接收expectedVersion，并在flush后生成包含新版本的事件。flush提前暴露并发异常，避免用旧版本构造后续事件。常见陷阱是在乐观锁异常后继续使用同一持久化上下文；事务可能已失败，正确做法是结束它，再在新事务重新获取状态。

本项目的状态机只允许TODO到IN_PROGRESS再到DONE，版本正确也不代表任意状态跳转合法。业务状态检查与版本竞争检查缺一不可；前端收到最新版本后也应重新判断用户意图，不能为了消除冲突自动把所有旧输入覆盖上去。

原始资料：PostgreSQL 并发控制。

条件扣减返回影响行数0，应如何解释？
查看判断依据

正确答案：本次未发生扣减。SQL正常执行但更新零行，表示本次条件未满足，没有完成业务扣减；应反馈失败条件，不能当作扣减成功。

把知识变成操作

用两个psql会话证明最后一件库存只可扣一次。

  1. 启动PostgreSQL，在A按本课建schema和表。
  2. A开启事务扣减后不提交；B开启事务执行同一UPDATE。
  3. A提交；观察B为UPDATE 0，B提交，查询quantity并清理本课schema。
验收信号

A更新1行，B更新0行，最终quantity=0，没有超卖。

做完再看：参考答案与排错线索

B等待A的行锁；A提交后，Read Committed下更新会重新检查当前行条件，quantity>0不成立。若A回滚，B有机会更新1行。实际API冲突应返回明确错误，不能盲目报告200。
