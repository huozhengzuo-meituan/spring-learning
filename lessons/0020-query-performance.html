分页、索引与 N+1

从查询计划判断性能问题，并避免把数据库当作无限内存列表。

约 35 分钟先修：19Java 21 · Boot 4.1
从你的前端经验出发

前端无限滚动只显示少量内容，不代表后端只处理少量数据；分页与索引决定数据库实际工作量。

本课服务于同一个目标：独立交付并排查可靠的业务后端。实验入口：独立 PostgreSQL / psql 性能实验。标注为教学片段或设计实验的代码需要按题目补入，不代表示例已实现该功能。

分页必须有稳定顺序

没有ORDER BY的结果不承诺顺序；只有created_at排序而时间重复时，页面边界也不稳定。加入唯一键作为排序补充能让同一快照下的顺序确定。offset分页便于跳页，但深页需要跳过大量记录，数据插入和删除也会使页面漂移。游标分页从上一页最后的排序键继续，适合时间线，但仍需明确并发修改时的产品语义。

Spring Data的Page通常包含总数，可能触发count查询；Slice只回答是否还有下一段，可减少总数成本。客户端传入的size必须限上限，不允许一个“分页接口”被size=1000000绕成全量导出。本项目限制size在1..100，并使用更新时间和ID组合排序；稳定顺序不等于跨多次请求拥有同一数据库快照。

原始资料：PostgreSQL EXPLAIN。

索引服务具体访问路径

B-tree索引适合多种等值、范围与排序访问，但不是每列加索引就更快。索引增加写入、存储和维护成本，组合索引列顺序也影响可用性。过滤条件、排序方式和返回列一起决定查询方案。先写实际SQL，再用接近真实规模的数据看计划，不用小表结果外推生产。

下面在psql创建临时数据，分别观察建索引前后计划。EXPLAIN ANALYZE会真的执行语句，尤其对UPDATE/DELETE不能当作只读命令随便用于生产。实验只执行SELECT并统计缓冲访问。优化器仍可选择顺序扫描，若它预计多数行都会命中，这可能正是合理选择。

CREATE TEMP TABLE lab_events AS
SELECT n AS id, n%100 AS owner_id, now()-n*interval '1 second' AS created_at
FROM generate_series(1,50000) n;
ANALYZE lab_events;
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM lab_events WHERE owner_id=7 ORDER BY created_at DESC,id DESC LIMIT 20;
CREATE INDEX ON lab_events(owner_id,created_at DESC,id DESC);
ANALYZE lab_events;
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM lab_events WHERE owner_id=7 ORDER BY created_at DESC,id DESC LIMIT 20;

N+1来自访问模式而非某个注解

先查20个任务，再循环为每个任务查用户，会产生1+20条SQL。ORM懒加载容易把额外查询隐藏在属性访问里，但手写JDBC也会制造相同问题。解决可选DTO投影、批量查询、适当join或entity graph，具体方案必须符合所需字段与分页语义。

给集合关联直接fetch join同时分页可能造成重复行、内存分页或其他意外，不能把“加一个fetch”当通用解药。先测SQL数量和行数，再选方案。缓存也不应作为掩盖糟糕查询的第一步，否则冷缓存仍然爆发。练习报告保留扫描方式、实际行数、缓冲读取与执行时间，同时注明测试数据规模。

读计划时区分估算行数与实际行数。如果估算偏差巨大，索引未被选择的原因可能是统计信息陈旧或列值分布不均。先更新统计并重新测量，再决定是否改变索引。缓存命中和预热会改变耗时，所以一次毫秒数不能作为唯一优化证据。
