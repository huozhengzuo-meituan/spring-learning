Lesson 16 / 48 · 03 · 数据库与事务

用 Flyway 管理数据库演进

把表结构变化做成可追踪、可重放的迁移。

约 30 分钟先修：15Java 21 · Boot 4.1
从你的前端经验出发

前端版本升级主要替换静态资源；后端部署还要让新旧代码与已有数据库兼容，数据不能随发版丢弃。

本课服务于同一个目标：独立交付并排查可靠的业务后端。实验入口：examples/task-service；PostgreSQL迁移观察。标注为教学片段或设计实验的代码需要按题目补入，不代表示例已实现该功能。

数据库结构也需要版本历史

Flyway将有版本的迁移按顺序应用，并在历史表记录执行情况与校验信息。创建表和后来添加字段是不同迁移，已经在共享环境执行过的版本脚本不应随意改写。否则新环境与老环境可能获得不同结构，历史校验也会暴露漂移。修复通常新增迁移，而不是把旧脚本改成“现在看起来正确”。

版本号表达执行顺序，描述表达意图，例如V1__create_tasks.sql。文件名、位置与数据库支持模块都必须正确。Boot 4中Flyway采用明确的starter，PostgreSQL还需要对应数据库支持；不要把依赖加上却没有读取启动日志，就假定迁移一定跑过。

原始资料：Spring Boot Database Initialization。

用扩展再收缩降低发布耦合

假设想把title改成summary。直接改列名可能让旧实例立刻失败。更稳妥的过程是先增加新列，让代码兼容读取与写入，分批回填旧数据，确认全部实例升级后再删除旧列。不是每次修改都要这么复杂，但遇到滚动发布、多服务共享数据库或大表时，必须先思考兼容窗口。

下面是独立教学迁移，不要复制覆盖task-service已有V1。第一份创建notes，第二份增加允许为空的description，第三步再讨论如何回填并收紧约束。给非空大字段加默认值、创建索引、修改类型都可能产生锁与执行时间，需要在接近真实数据规模下验证。

-- 教学 V1__create_notes.sql
CREATE TABLE notes (
  id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  title varchar(120) NOT NULL
);

-- 教学 V2__add_description.sql
ALTER TABLE notes ADD COLUMN description text;

-- 查看历史：在实际应用数据库执行
SELECT installed_rank, version, description, success
FROM flyway_schema_history ORDER BY installed_rank;

原始资料：Flyway 官方文档。

迁移失败与回滚要提前设计

开发阶段使用Hibernate自动建表很方便，但生产结构应由一种明确的迁移策略管理；不要混用schema.sql、自动ddl更新和Flyway争抢同一张表。应用可以用映射校验发现不匹配，却不应在启动时悄悄随意重塑生产结构。H2能证明部分流程，但不能证明PostgreSQL的DDL锁行为与方言。

Flyway成功不意味着业务数据回填已正确；迁移脚本应验证数量、约束和兼容性。灾难恢复靠备份与恢复演练，不能假定任何DDL都有简单反向语句。repair修改历史元数据，也不是删除失败证据的快捷键。先确定实际结构和失败原因，再决定修复路径。

创建全新数据库与升级已有数据库都要测试。前者证明迁移链可以从零重放，后者证明真实旧数据满足新增约束。只测空库经常漏掉历史NULL、重复值或字段长度超限，所以部署前要用脱敏且具有代表性的数据验证升级路径。

原始资料：Flyway 官方文档。
