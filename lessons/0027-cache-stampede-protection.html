Lesson 27 / 48 · 05 · Redis 与缓存

穿透、击穿、雪崩：把回源流量限制住

根据故障的流量形状选择保护措施，并计算缓存失效时的数据库压力。

约 30 分钟先修：第26课：缓存一致性Java 21 · Boot 4.1
从你的前端经验出发

前端 debounce 合并一次操作；后端必须合并多个线程甚至多个实例对同一热点键的回源。

本课服务于同一个目标：独立交付并排查可靠的业务后端。实验入口：独立 jshell + 故障设计实验。标注为教学片段或设计实验的代码需要按题目补入，不代表示例已实现该功能。

三个名字对应三个不同输入

穿透是请求不存在的数据，缓存和数据库都找不到却反复查询；击穿是一个极热点键失效后大量请求一起回源；雪崩是许多键同时失效或者整个缓存不可用。先观察“哪些 key、何时、多少请求”再定策略。对不存在资源短暂缓存明确的空结果，可以减少重复查找，但必须区分“确定不存在”和“数据库报错”。把故障当空值缓存，会把短暂错误变成持续假404。所有回源都要受并发和时间预算约束。

给保护措施配上代价

负缓存需要短 TTL 以及资源新建后的失效，否则刚创建的数据暂时看不到；Bloom filter 能快速排除明确不存在的集合成员，但“可能存在”仍要查询，而且过滤器的数据更新也是系统的一部分。热点重建可以做单进程 single-flight，多副本场景需要各自预算或额外协调。对允许陈旧的数据可以返回旧值并异步刷新。随机 TTL 分散失效时刻，不能修复 Redis 整体断网。每个策略都要写出代价与不适用数据。

先做一个容量计算

假设总流量 2000 次每秒，正常命中率 95%，数据库只承受约 100 次每秒；缓存完全失效后可能变成 2000 次每秒。数据库容量若是 300 次每秒，仅增加重试会使故障更重。应限制回源并发、限制等待队列，并对非关键功能快速失败或返回明确的陈旧数据。下面在 jshell 中计算 TTL 抖动范围，只展示策略，不构成完整缓存实现。

import java.util.concurrent.ThreadLocalRandom;
int baseSeconds = 300;
int ttl = baseSeconds + ThreadLocalRandom.current().nextInt(0, 61);
System.out.println(ttl); // 每个键分散到300~360秒
double originQps = 2000 * (1 - 0.95);
System.out.println(originQps); // 约100次/秒

演练要有停止条件

只在隔离的开发环境演练。先记录正常数据库延迟与连接池占用，再只删除一个课程键观察回源；下一步才模拟缓存不可达。设定停止条件，例如错误率超过百分之一或连接池等待持续增加就结束实验。成功证据包括回源峰值有上限、没有无界队列、缓存恢复后命中回升、负缓存没有掩盖系统错误。日志里记录保护策略选择而非每次输出整份业务数据。能说明未命中原因，比背诵三个术语更有价值。

一手阅读：Redis 淘汰策略与内存限制；Spring Redis Cache。带着本课实验的输出阅读；有任何不清楚的步骤，可以直接把命令和结果发给学习助手继续追问。

热点保护还要给等待者设置超时；如果负责重建的请求失败，其他请求必须能得到失败或重试机会，不能永远等待一个不会完成的结果。单进程请求合并的测试可以用十个并发调用和一次被计数的回源函数，检查同一键被合并，不同键仍可独立推进。

合上笔记，先判断

整个 Redis 不可用时，哪项措施直接限制数据库冲击？
查看判断依据

正确答案：限制回源并发。TTL与空值都依赖缓存正常可用。缓存不可用时，回源并发、队列和超时预算才直接保护数据库。

把知识变成操作

为任务详情写一张可执行的缓存故障处理表。

  1. 列出不存在ID、单热点过期、所有缓存断连三类输入。
  2. 分别填写返回内容、TTL或等待上限、最大回源并发。
  3. 用2000 QPS和95%命中率计算正常回源量。
  4. 增加资源新建和数据库报错两例，检查负缓存是否误伤。
验收信号

至少五个场景均有明确反馈；正常回源100 QPS，完全失效20倍，预算不能缺失。

做完再看：参考答案与排错线索

不存在可短暂负缓存；热点用请求合并；整体故障用有界回源和降级。数据库异常必须返回或记录真实失败，不能伪装为资源不存在。
