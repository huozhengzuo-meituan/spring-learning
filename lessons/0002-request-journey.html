从浏览器请求走到 JVM

沿请求链定位网络、路由、业务和序列化错误。

约 25 分钟先修：01Java 21 · Boot 4.1
从你的前端经验出发

前端的 fetch 只是链路起点；后端需要把字节转成参数、执行业务，再按协议返回字节。

本课服务于同一个目标：独立交付并排查可靠的业务后端。实验入口：examples/hello-api。标注为教学片段或设计实验的代码需要按题目补入，不代表示例已实现该功能。

先把边界画清楚

一次请求通常依次经过浏览器、网络连接、服务器端口、Servlet 容器、过滤器、Spring MVC 分发器、控制器和业务方法。响应再经消息转换器写回网络。Spring Boot 帮你启动嵌入式容器，但不会把网络变成本地函数调用：连接可能失败，请求可能超时，响应可能已经生成却没有到达客户端。

因此“前端报错”需要拆分。连接拒绝通常说明端口没有服务监听；404 说明 HTTP 已有响应但资源没找到；400 往往说明输入未满足解析或校验要求；500 指向服务器无法正常完成。浏览器的跨域错误也可能发生在服务已经返回之后，必须同时看 Network、服务器日志和 curl 结果。

原始资料：HTTP 语义规范 RFC 9110。

协议是两端共同的合同

URL 路径表达资源位置，查询参数表达筛选或分页；请求头描述内容格式和认证，body 承载结构化数据。Content-Type 声明发送的表示类型，Accept 表达接收方希望获得的类型，两者不能互换。JSON 字段虽然看起来与 JavaScript 对象接近，但它只是文本协议；Java 类型、日期格式、空值和数值范围都必须约定。

后端不应该相信前端隐藏了按钮就代表请求无法发出。任何人都可用 curl 构造请求。服务器必须独立检查参数和权限；前端校验承担及时反馈，后端校验承担边界保护。观察请求时先记录 method、path、status，再记录敏感信息已脱敏的业务字段。

curl -i http://localhost:8081/api/tasks
curl -i http://localhost:8081/no-such-route
curl -i -X POST http://localhost:8081/api/tasks \
  -H "Content-Type: application/json" \
  --data '{"title":"追踪一次请求"}'

原始资料：Spring MVC 文档。

不要混淆请求失败与业务未执行

假设创建任务已成功写入，响应在网络中断时丢失，前端只会看到失败。如果立即重试，服务器可能创建第二条任务。这说明 HTTP 客户端的异常不能直接证明后端没有执行，后续会通过幂等键处理这个问题。现在先养成习惯：提交后用查询验证状态，不以界面提示作为唯一证据。

服务线程也不同于浏览器中的单个页面。多个用户的请求会并行进入同一个 JVM，甚至访问同一个控制器实例。请求局部变量适合保存本次处理信息；用户身份、请求对象和临时数据不应放在共享字段。后面理解单例 Bean 时，再把这里的请求链与对象生命周期连接起来。

原始资料：Spring MVC 文档。

流程可写为 curl→TCP端口→容器→过滤器→DispatcherServlet→Controller→Service→消息转换器。连接失败停在入口之前；404发生在已有HTTP服务之后；POST成功后再次GET可确认新任务。
