读懂 Maven 与依赖管理

从 pom 和依赖树解释一个类为何出现在运行时。

约 25 分钟先修：03Java 21 · Boot 4.1
从你的前端经验出发

package.json 告诉你项目依赖什么；pom 还描述编译、测试、打包及依赖版本管理。BOM 接近一组经过协调的版本约束。

本课服务于同一个目标：独立交付并排查可靠的业务后端。实验入口：examples/hello-api。标注为教学片段或设计实验的代码需要按题目补入，不代表示例已实现该功能。

依赖坐标与生命周期

Maven 用 groupId、artifactId、version 定位构件，依赖又会带入传递依赖。你只声明 Web MVC starter，项目中仍会出现 Spring MVC、JSON 库和容器，这是正常的依赖图展开。compile 范围面向编译与运行，test 范围用于测试，runtime 范围常用于 JDBC 驱动等运行时组件；把测试库放进生产 classpath 会增加体积和攻击面。

clean、test、package、verify 不是任意脚本名。它们属于构建生命周期，调用后面的阶段会经过前面的必要阶段；verify 是否执行集成测试，取决于项目插件配置，不能只凭名称推断覆盖面。定位构建失败时先看出错阶段，再看第一个有因果意义的错误。

BOM 管版本，不自动添加依赖

Boot 的 parent 带来依赖与插件管理；企业已有 parent 时，可以改为导入 Boot BOM，但插件管理要另行配置。dependencyManagement 定义依赖版本规则，不会把所有管理条目都装进项目。只有 dependencies 或传递依赖真正引用时才进入依赖图。不要看到某库受 Boot 管理，就以为它已经可用。

直接指定底层 Spring、Jackson 或 Hibernate 的版本可能打破整套兼容关系。确需安全修复或功能升级时，记录为何覆盖、覆盖了哪条依赖链，并运行验证。两个依赖要求不同版本时，应先用依赖树找来源，不能通过反复加版本号“消除红线”。

./mvnw -f examples/hello-api/pom.xml dependency:tree
./mvnw -f examples/hello-api/pom.xml help:effective-pom
./mvnw -f examples/hello-api/pom.xml dependency:tree '-Dincludes=org.springframework:*'
# 理解版本管理：下面仅是 POM 片段，不要求重复添加
# <properties><java.version>21</java.version></properties>

Boot 4 的模块化需要读当前文档

本课程 MVC 使用 spring-boot-starter-webmvc；相应测试功能可使用 spring-boot-starter-webmvc-test。Boot 4 将多个自动配置和测试功能拆成更明确的模块，因此旧教程的 starter 和 import 不能只靠名称猜测。若一个测试注解导入失败，先确认测试模块是否添加以及包名是否迁移。

构建输出里一个依赖的版本号不等于它的生产使用情况：它可能只在测试范围、被冲突选择淘汰，或者属于插件依赖。把源代码 import、pom 声明、最终依赖树三者对应起来，才算真正找到来源。练习中不需要升级任何库，只练习解释当前项目为何能够编译。

Maven的传递依赖选择也不等同于npm把不同版本放进嵌套目录。Java运行时常要在同一classpath上使用选中的类定义，二进制方法签名不匹配会出现NoSuchMethodError等问题。遇到运行期缺方法，既要查编译时依赖，也要查实际运行产物中的版本。

正确答案：只提供版本规则。管理条目不等于实际依赖声明，仍需 dependencies 或传递依赖引用。

把知识变成操作

解释 hello-api 中任意一个 Spring 类的依赖来源。

  1. 执行 dependency:tree，找到 spring-webmvc 及其上游。
  2. 执行 effective-pom，搜索 java.version 与 Boot parent。
  3. 记录一个测试依赖及其 scope，不修改版本。
