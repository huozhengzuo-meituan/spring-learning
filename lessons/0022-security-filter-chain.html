认证、授权与过滤器链

分清身份验证和权限判断，并对默认拒绝策略做验证。

约 30 分钟先修：21Java 21 · Boot 4.1
从你的前端经验出发

前端路由守卫用于体验，真正的权限边界必须在服务端，因为请求可以绕过页面直接发送。

本课服务于同一个目标：独立交付并排查可靠的业务后端。实验入口：examples/task-service。标注为教学片段或设计实验的代码需要按题目补入，不代表示例已实现该功能。

进入控制器之前就可能被拒绝

Spring Security基于Servlet过滤器链处理认证、授权及常见保护。认证回答当前是谁，授权回答这个身份能否执行这次操作。身份信息被组织为Authentication及其权限；控制器还没运行，请求就可能因缺少凭据被拒绝。因此在ControllerAdvice里找不到401的来源并不奇怪。

Basic认证把用户名密码按协议编码发送，编码不是加密，真实传输必须有TLS。课程本地reader和writer仅用于观察规则，内存账号不是生产账号体系。密码在服务端用专门的PasswordEncoder校验，不保存明文，更不把普通SHA摘要当作现代口令存储方案。

原始资料：Spring Security Servlet Architecture。

规则按实际路径和方法设计

本项目GET任务需要READER，POST和PATCH需要WRITER，其他未明确允许的路径默认denyAll。writer同时具有READER权限，因此可以读写；reader只有读取权限。公开健康检查与受限运维端点也应区分。路径匹配顺序重要，宽泛permitAll写在前面可能使后面的细规则失去预期作用。

角色一般映射到带ROLE_前缀的权限；hasRole("WRITER")与hasAuthority("ROLE_WRITER")有对应关系，但不能在hasRole里机械地重复加前缀。更细粒度业务权限可用方法级授权或明确服务检查，但注解不是资源所有权校验的替代。知道任务ID不意味着有权读取别人的任务。

./mvnw -f examples/task-service/pom.xml spring-boot:run

测试拒绝路径时排除其他保护干扰

匿名读取通常触发401，错误密码也应拒绝，有效reader读取成功。测试reader写入权限时，必须同时提供有效CSRF token，否则可能先被CSRF拒绝，无法证明角色规则真的起作用。这类多个防线共同存在的场景，需要一次只改变一个条件，才能解释403由谁产生。

当前示例没有完整多租户和对象所有权模型，作为生产系统扩展时需要添加任务owner以及服务端关联验证。不要因为接口已经有SecurityFilterChain就宣称完整鉴权。练习产物是一张身份、方法、路径、预期结果的权限矩阵，后续每次新增路由都要补进去。

权限矩阵应包含允许和拒绝两组案例。新增接口最容易出现遗漏，因此默认拒绝能让未声明行为显式失败。默认拒绝只是安全基线，不能替代清晰产品权限定义；真正的要求来自谁能对哪份资源执行什么动作，并通过测试持续保持。

原始资料：Spring Security HTTP Authorization。
