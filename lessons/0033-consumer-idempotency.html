至少一次投递与消费幂等

为数据库副作用设计可重试且只生效一次的消费事务。

约 30 分钟先修：第32课：消费组进度 / 数据库事务与唯一约束Java 21 · Boot 4.1
从你的前端经验出发

按钮防重复点击只保护一个页面；后端必须面对网络重试、进程崩溃和消息重放带来的重复。

本课服务于同一个目标：独立交付并排查可靠的业务后端。实验入口：独立 PostgreSQL 事务设计；task-service events-count 可作已实现路径观察。标注为教学片段或设计实验的代码需要按题目补入，不代表示例已实现该功能。

把崩溃点画在两次提交之间

先提交offset再改数据库，进程在中间崩溃会漏处理；先改数据库再提交offset，中间崩溃会重复处理。把两个步骤换顺序无法消除窗口。常用做法是接受至少一次到达，通过业务幂等使重复到达不重复产生副作用。幂等不只是“重复调用返回成功”，而是相同业务请求再次执行，结果仍满足预期。一个累加计数器天然不幂等，按实体版本条件更新或按eventId唯一约束就能把重复识别出来。

去重记录与业务写入同一事务

以下是 PostgreSQL 设计片段，使用独立学习表，不直接修改当前项目迁移。去重键包含订阅者名称：两个不同用途消费者都应有机会处理同一事件。INSERT返回是否插入成功；只有新插入时执行业务更新。两者必须在同一个数据库事务中，若业务失败整个事务回滚。不能先向Redis写去重标记，再修改数据库；那会在失败后把尚未完成的业务永远跳过。

CREATE TABLE course_consumed_event (
  subscriber varchar(80) NOT NULL,
  event_id uuid NOT NULL,
  consumed_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (subscriber, event_id)
);
-- 与业务UPDATE放在同一事务；返回0行表示本订阅者已处理。
INSERT INTO course_consumed_event(subscriber,event_id)
VALUES ('task-counter', '00000000-0000-0000-0000-000000000033')
ON CONFLICT DO NOTHING
RETURNING event_id;

处理顺序和投递重复是两件事

同一eventId重复是去重问题；不同eventId但旧业务版本晚到是顺序问题。例如任务v4完成后收到v3进行中，eventId都不同，单纯去重仍会回退状态。要比较aggregateVersion，按规则拒绝过时更新，或在需要完整连续事件时检测版本缺口并等待补偿。Kafka事务在Kafka读写链路内有价值，但不会自动把普通数据库更新或发送邮件包括进来。邮件、支付等外部副作用需要对方支持幂等键或独立可恢复投递状态。

以崩溃测试证明结果

最小验证是同一个eventId消费两次，业务计数只增加一次；更强验证是在数据库提交后、offset提交前故意终止隔离消费者，重启后同一事件重放但计数不增加。再测业务抛错时去重行也回滚，使下一次仍可处理。去重表需要保留策略，不能比消息可能重放的窗口更短而不说明风险。记录重复计数用于了解系统行为，频繁重复可能是重平衡或失败重试，不应把它们全部当成无关噪声。

数据库重复键也可能来自完全不同的业务冲突，因此要按约束名称和事件身份分类。只有“同一订阅者已经处理过这个事件”才能作为幂等成功；其他唯一约束冲突应保留失败并调查，否则消费者会把真实数据质量问题悄悄跳过。
