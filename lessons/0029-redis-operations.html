Lesson 29 / 48 · 05 · Redis 与缓存

Redis 持久化、复制与集群运维

区分可恢复、高可用和可扩展，并写出一次可验证的恢复计划。

约 30 分钟先修：第28课：原子与锁Java 21 · Boot 4.1
从你的前端经验出发

前端缓存通常清空即可；后端Redis若承载会话或队列，重启后的损失会影响用户业务。

本课服务于同一个目标：独立交付并排查可靠的业务后端。实验入口：Redis CLI 只读观测 + 隔离恢复设计。标注为教学片段或设计实验的代码需要按题目补入，不代表示例已实现该功能。

三个能力回答不同问题

持久化回答进程重启后能恢复多少数据；复制与故障切换回答一个节点故障时谁提供服务；分片回答单机容量或吞吐不足时如何分摊。RDB 保存时间点快照，AOF 记录写入并按策略刷盘；它们都有资源开销和恢复时间。复制通常异步，主节点确认给客户端的最近写入仍可能在故障切换后丢失。不能把“有副本”直接翻译为“绝不丢数据”，也不能把 AOF 文件存在翻译为“备份一定可用”。

先读运行状态再调参数

下面都是观察命令。INFO memory 观察使用量和淘汰相关背景，INFO persistence 观察持久化运行状态，INFO replication 观察角色与复制进展，SLOWLOG 看服务器命令执行慢的记录。客户端超时还可能来自网络或排队，不能只根据 SLOWLOG 没有慢命令就认定服务正常。容量预算需要给复制缓冲、持久化 fork 的写时复制等留空间。开发 Compose 单节点只是功能演示，不是高可用拓扑。

docker compose exec redis redis-cli INFO memory
docker compose exec redis redis-cli INFO persistence
docker compose exec redis redis-cli INFO replication
docker compose exec redis redis-cli SLOWLOG GET 5
docker compose exec redis redis-cli CONFIG GET maxmemory-policy

Sentinel 与 Cluster 的边界

Sentinel 侧重监测主从和故障转移；Cluster 把键分到哈希槽，组合分片与各分片的复制故障转移。客户端要支持拓扑变化与重定向，多key操作需要考虑槽位置。Hash tag 可以让相关键同槽，但滥用会产生热点。系统上云后通常使用托管产品提供部署与备份能力，应用仍负责超时、重连、幂等和容量规划。运维设计要分别回答少量数据丢失容忍度RPO和恢复时间目标RTO，而非只写“使用集群”。

恢复练习才验证持久化

本课程不要求清空已有卷来测试。创建专用隔离实例和命名学习数据，记录持久化配置，在持续写入期间正常停止再恢复，比较预期条数；另做异常停止实验，记录可能损失窗口。备份必须尝试在新的实例恢复，并检查业务可读，而不是只比较文件大小。缓存型数据可以选择重建，但重建时仍需要第27课的回源保护；会话等非缓存数据则必须明确用户影响。演练结论包括配置、命令、数据差异和耗时。

一手阅读：Redis 持久化；Redis 复制；Redis Cluster 规范。带着本课实验的输出阅读；有任何不清楚的步骤，可以直接把命令和结果发给学习助手继续追问。

不要为了排查性能在生产直接运行长时间MONITOR；逐条追踪命令本身有额外开销，还可能暴露业务内容。先使用已有指标、慢日志和有限采样。容量告警也需要趋势：内存尚未满但持续增长，可能比一次短暂高峰更需要定位键增长来源。

把知识变成操作

为任务详情缓存和登录会话分别制定 Redis 恢复策略。

  1. 运行五条观察命令，保存角色、持久化状态和淘汰策略。
  2. 写下两类数据的RPO/RTO以及可否从数据库重建。
  3. 只为隔离实例设计“写入—停机—新实例恢复—读回”的步骤。
  4. 写出恢复后缓存回源洪峰如何限流。
验收信号

能区分主从切换与备份恢复；策略包含业务损失和容量约束。
