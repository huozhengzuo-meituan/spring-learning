Lesson 36 / 48 · 06 · Kafka 与事件一致性

事件 schema 演进与契约测试

设计旧消费者仍能理解的新事件，并保存可运行的契约样本。

约 30 分钟先修：第30课：事件 / 第35课：错误处理Java 21 · Boot 4.1
从你的前端经验出发

前端API升级要兼容旧客户端；Kafka还要兼容磁盘里几周前留下的旧事件和晚升级的消费者。

本课服务于同一个目标：独立交付并排查可靠的业务后端。实验入口：独立契约fixtures设计；task-service为后续实现载体。标注为教学片段或设计实验的代码需要按题目补入，不代表示例已实现该功能。

事件会活得比一次部署更久

发布者和消费者通常无法同时升级，历史日志也不会随着代码更新自动迁移。因此一个事件契约至少定义字段含义、类型、必填性、默认值、枚举扩展规则和版本策略。数据库实体对象不是稳定事件契约：重命名表字段不应该意外改变对外消息。使用专门事件DTO或schema，并保持eventId与实体ID职责不同。发生时间用明确时区的格式，金额用最小货币单位或明确十进制规则，避免JavaScript数字范围与Java long不一致。

添加字段也不是自动安全

新增可选字段，且旧消费者忽略未知字段时，常常能兼容；新增必填字段则使旧历史记录无法解析。字段改名、类型变化、含义变化通常破坏兼容。枚举新增值也可能打破旧客户端的穷尽switch。若用JSON，应显式约定未知字段与未知枚举处理；Boot4采用Jackson3，不能想当然复制旧com.fasterxml相关数据绑定import。Avro、Protobuf或JSON Schema与schema registry可以帮助自动检查，但仍不能判断“金额从元变成分”的业务含义变化。

为演进保存具体样本

下面两份原创样本表达同一个事实。v2新增可选actorDisplayName；消费的关键字段是eventId、taskId、type和aggregateVersion。把两份JSON作为契约fixtures，分别喂给新消费者测试；再用旧消费者验证v2是否能被接受。若无法兼容，就建立新事件类型或明确迁移期，不要让version字段只是装饰。

// v1 fixture（真正保存为JSON时去掉注释）
{"eventId":"e-36","taskId":"42","type":"TaskCompleted",
 "schemaVersion":1,"aggregateVersion":3}
// v2 fixture
{"eventId":"e-36","taskId":"42","type":"TaskCompleted",
 "schemaVersion":2,"aggregateVersion":3,"actorDisplayName":"Lin"}

契约验证与业务验证配合

契约测试检查序列化、字段约束与兼容性；业务测试检查旧版本事件不会覆盖新状态；端到端测试检查真实broker上的序列化器与配置。三者互补，单独一个不够。契约变更应记录生产者版本、受影响消费者、回滚方式与历史重放是否支持。不要在生产者和消费者测试中共享同一份错误实现，然后以“双方都通过”证明契约正确；保留独立预期fixture更容易发现无意变化。毕业项目将要求至少一次兼容字段演进和旧样本回放。

一手阅读：OpenAPI Schema 与JSON Schema语义；Debezium Outbox 消息结构。遇到不明白的输出、时序或取舍，请把你的推理发给学习助手继续追问。

兼容测试还要覆盖字段值边界：空字符串与缺失字段不是同一回事，零与未知金额也不是同一回事。为标识符、日期和枚举各保存一个边界样本，可以避免默认值悄悄改变业务含义。契约文件应与代码一起审查，变更说明要让消费者维护者看得懂。

最适合作为兼容演进起点的是哪种变更？
查看判断依据

正确答案：新增可选字段。新增可选字段仍需验证旧消费者容忍未知字段；更改含义或删除必填字段通常破坏契约。

把知识变成操作

为TaskCompleted写一组新旧契约测试用例。

  1. 保存v1与v2两份合法JSON样本。
  2. 设计缺少可选字段、未知字段、未知枚举、缺少eventId四个输入。
  3. 为每种输入写接受或拒绝，以及错误证据。
  4. 说明schemaVersion与aggregateVersion为什么不能合并。
验收信号

兼容样本可读；缺少eventId不能悄悄生成新ID；业务版本仍独立用于防乱序。

做完再看：参考答案与排错线索

schemaVersion描述消息结构；aggregateVersion描述实体业务进展。缺失身份应进入明确失败流程，而不是每次重试换新ID。
