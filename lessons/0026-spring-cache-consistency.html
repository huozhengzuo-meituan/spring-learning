Lesson 26 / 48 · 05 · Redis 与缓存

Spring Cache 与 cache-aside 一致性

画出缓存与数据库并发时序，区分注解简化与一致性保证。

约 30 分钟先修：第25课：Redis 数据模型 / 事务与代理基础Java 21 · Boot 4.1
从你的前端经验出发

像前端查询缓存一样，后端缓存也要设计 key、失效和陈旧窗口；但后端有多副本和数据库事务。

本课服务于同一个目标：独立交付并排查可靠的业务后端。实验入口：独立 Redis CLI + 时序设计实验。标注为教学片段或设计实验的代码需要按题目补入，不代表示例已实现该功能。

先明确谁保存真实数据

cache-aside 的读取是：查缓存，未命中再查数据库，回填缓存后返回。写入通常先提交数据库，再删除相应缓存。数据库是事实来源，缓存是可重建副本。Spring Cache 是抽象层，可以接本地缓存或 Redis；@Cacheable 让一次成功计算可复用，@CacheEvict 表达删除。它们不替你定义可接受的陈旧时间，更不把数据库与 Redis 组成一个原子事务。不同用户看到的任务权限不同，key 必须考虑数据作用域。

读懂注解背后的拦截

下面是独立教学片段，需要启用缓存并提供 CacheManager；不是给现有项目直接加上的已验证功能。#p0 用参数位置避免依赖编译保留的参数名。默认代理模式下，同一对象内部自调用不会经过缓存代理。返回 DTO 比缓存持久化实体更容易控制序列化与版本。Redis Cache 的 TTL、空值策略和序列化器需要显式设计；Boot 4 的 Jackson 3 生态下尤其不要照搬旧教程的类型和配置。

@Cacheable(cacheNames = "task-detail", key = "#p0")
public TaskView find(long id) {
    return repository.loadView(id); // 教学片段：由调用方承担不存在语义
}

// 使用独立的提交后事件处理器删除缓存，避免事务未提交先删。
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void invalidate(TaskChanged event) {
    cacheManager.getCache("task-detail").evict(event.id());
}

提交后删除仍然存在竞争

时间线：读请求 A 缓存未命中，读取数据库旧值 v1；写请求 B 提交 v2 并删除缓存；A 最后把 v1 放回缓存。虽然 B 完全遵守先写后删，旧数据仍可存活到 TTL。删除也可能因为 Redis 断开而失败。根据业务选择短 TTL、可靠失效事件、带版本的回填控制，或对强一致读取绕过缓存。延迟双删只是缩小某些窗口，不能凭一个固定睡眠时间证明所有并发和故障情形都正确。

观察命中并保留降级预算

先测数据库查询次数，再谈缓存命中率；命中很高但详情长期陈旧也不是成功。定义指标：命中、未命中、回源耗时、删除失败数、读取到的业务版本。Redis 超时后能否回源取决于数据库余量，不能无限并发回源。task-service 中已实现哪些缓存路径应以项目 README 和测试为准；本课目标是审查设计以及完成一个可复现实验，不要求把所有读操作一股脑缓存。你应能解释为什么列表页缓存比单条详情更难失效。

一手阅读：Spring Cache 注解；Redis Cache 配置。带着本课实验的输出阅读；有任何不清楚的步骤，可以直接把命令和结果发给学习助手继续追问。

还要检查事务事件的注册位置：只有在实际事务中发布，提交后监听语义才有意义；异步监听失败仍需可靠记录和重试。对于课堂练习，先用时序图证明你接受的陈旧窗口，再决定引入何种补偿，避免把越来越多注解误当成越来越强的一致性。

合上笔记，先判断

数据库事务提交成功且缓存删除成功，可以推出什么？
查看判断依据

正确答案：仍有并发旧回填。先读旧值再延迟回填的请求，可能发生在提交后删除之后；需要额外设计或接受有界陈旧。

把知识变成操作

用三个 Redis 命令模拟旧值回填，记录失效策略的边界。

  1. 将纸上的数据库值写为 v1，读请求 A 记录 v1 但暂不回填。
  2. 把纸上数据库更新为 v2，然后 DEL course:race。
  3. 模拟 A 执行 SET course:race v1 EX 30，再 GET。
  4. 写出“可陈旧30秒”和“写后立即读新值”两种需求的不同方案。
验收信号

缓存为 v1，数据库为 v2；命令全部成功仍会出现陈旧。

做完再看：参考答案与排错线索

对有界陈旧可用短TTL和失败失效补偿；写后强一致读可绕过缓存读主库，不能仅靠CacheEvict承诺。
