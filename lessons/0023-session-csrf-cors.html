Session、CSRF 与 CORS

用同一会话完成合法写请求，并说明CSRF与跨域的不同边界。

约 35 分钟先修：22Java 21 · Boot 4.1
从你的前端经验出发

浏览器自动携带Cookie让登录方便，也使跨站伪造请求有机会借用你的身份；跨域策略又是另一套浏览器规则。

本课服务于同一个目标：独立交付并排查可靠的业务后端。实验入口：examples/task-service。标注为教学片段或设计实验的代码需要按题目补入，不代表示例已实现该功能。

自动携带凭据带来的风险

Session将部分登录状态保存在服务器，浏览器通过Cookie引用会话。CSRF攻击利用浏览器会向目标站点自动发送凭据的特点，诱导用户访问恶意页面后提交状态修改请求。防护需要验证攻击者无法取得的token或采用经过审查的其他机制；不能因为接口叫REST就关闭CSRF。

Basic凭据也可能被浏览器缓存并自动携带，所以本项目保留CSRF。SameSite Cookie能减少一些跨站场景，但不替代所有应用边界分析。HttpOnly帮助阻止脚本直接读取Cookie，却不阻止浏览器自动发送；Secure限制HTTPS传输，三者解决的问题不同。XSS仍可在同源上下文做很多事情，应单独防护。

原始资料：Spring Security CSRF。

让token与会话保持一致

本项目GET /api/csrf返回headerName和token，同时可能建立会话Cookie。后续POST需要带回同一Cookie，并按返回的headerName发送token。只复制token而丢掉会话，会导致服务器找不到对应的期望值。不要将CSRF token误认为登录令牌，它不替代用户名密码或其他认证信息。

下面使用curl、临时Cookie文件和Python标准库完成流程。演示账号仅适用于本机学习服务。故意省略token时预期403；保留同一Cookie并提供token时writer可以创建任务。变更用户或重新登录后按应用流程重新获取token，不把某次采集的值永久硬编码进前端。

learning_cookie=$(mktemp)
learning_csrf=$(curl -fsS -u writer:writer-local-only -c "$learning_cookie" \
  http://localhost:8080/api/csrf)
learning_header=$(printf %s "$learning_csrf" | python3 -c 'import json,sys; print(json.load(sys.stdin)["headerName"])')
learning_token=$(printf %s "$learning_csrf" | python3 -c 'import json,sys; print(json.load(sys.stdin)["token"])')
curl -i -u writer:writer-local-only -b "$learning_cookie" \
  -H "$learning_header: $learning_token" -H "Content-Type: application/json" \
  --data '{"title":"验证CSRF"}' http://localhost:8080/api/tasks
rm "$learning_cookie"

原始资料：Spring Security CORS。

CORS不等于认证，也不等于CSRF

CORS告诉浏览器哪些来源允许读取跨域响应，预检请求通常不携带登录Cookie，所以CORS处理需要在Security正确的位置完成。配置精确来源、允许的方法和头，携带凭据时不能随意使用通配来源。curl不执行浏览器CORS限制，curl成功不代表前端跨域一定成功。

攻击者仍可用非浏览器客户端发请求，因此CORS不是服务端认证。某些跨站请求可以被发送但响应不可读，业务修改仍可能发生，所以也不能把CORS当作CSRF替代。本地联调可采用开发代理保持浏览器同源，或明确配置受信任源；不要遇到403就一口气关闭CSRF、授权和CORS检查。

同源由协议、主机和端口共同决定，因此本机8080与前端开发端口也属于不同源。所谓同站点又是Cookie语义中的另一概念，别把二者混用。调试时记录页面Origin和实际请求目标，再看预检响应，不要只因为两边都写localhost就推断无需CORS。

原始资料：Spring Security CORS。

查看判断依据

正确答案：浏览器跨域读取。CORS由浏览器执行，不能替代认证、授权或CSRF保护。

把知识变成操作

证明CSRF token与会话配套，并单独验证reader写权限。

  1. 先用writer直接POST不带token，记录403。
  2. 执行完整token与Cookie流程，确认创建成功。
  3. 重新用reader获取自己的Cookie和token，再POST合法title，确认仍被拒绝。
验收信号

writer无token为403，有匹配token成功；reader即使token正确也为403。

做完再看：参考答案与排错线索

第一种失败由CSRF造成；第二种通过证明会话与token配套；第三种在有效认证和CSRF前提下仍失败，才支持“reader没有WRITER权限”的结论。CORS实验必须用真实浏览器来源验证。
