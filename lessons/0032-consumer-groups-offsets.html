消费组、offset 与重平衡

用消费组观察进度，并分析处理时间、提交时机和重平衡的关系。

约 30 分钟先修：第30课：分区 / 第31课：投递确认Java 21 · Boot 4.1
从你的前端经验出发

前端分页游标表示下次从哪里开始；Kafka已提交offset也代表恢复时下一条位置，而不是业务处理的自动证明。

本课服务于同一个目标：独立交付并排查可靠的业务后端。实验入口：独立 Kafka CLI。标注为教学片段或设计实验的代码需要按题目补入，不代表示例已实现该功能。

区分三个位置

broker日志末端说明已经写到哪里；消费者当前position说明下一次将读取哪里；已提交offset说明故障恢复从哪里开始。拉取一批记录会推进读取位置，但这批记录的业务处理可能还没结束。lag通常反映日志末端与消费组提交位置的差距，不能仅凭lag为零证明外部数据库处理一定正确。消费组ID是持久身份：更换groupId相当于另一个订阅者，它不会自动继承旧组的处理进度。

用CLI看见消费组

在第30课主题上启动指定group的消费者，输入少量事件，然后查看group状态。控制台消费者用于观察机制，不代表已经具备数据库安全提交的业务消费者。--from-beginning只影响没有有效已提交位置时的起点策略，不会每次强制覆盖一个已有组的offset。重置offset属于运维操作，必须先停止相关消费者，在隔离主题使用 dry-run 查看范围后再执行。

docker compose exec kafka /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic course.tasks --group course-inspect --from-beginning
# 另一个终端查看进度与lag：
docker compose exec kafka /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group course-inspect

重平衡重新分配责任

实例启动、离开或失联等会触发分区责任变化。业务处理若长时间不返回到poll循环，可能超过max.poll.interval.ms，导致自己失去分区后仍在处理旧数据，提交时失败。减少max.poll.records、缩短批次处理、异步架构下有序管理完成位置，比简单把超时调成几小时更可控。不要把KafkaConsumer实例随意跨线程共享。offset提交到更后位置意味着前面的记录也被视为完成，某条失败时不能跳过后续完成状态随便提交。

Spring容器仍需要明确策略

Spring Kafka提供容器管理poll与提交，默认行为需要按当前配置和AckMode确认。业务代码通常让成功返回代表本次处理完成，失败抛出异常交给错误处理；吞掉异常会把失败伪装成成功。手动ack只提供控制点，不会自动把数据库提交和Kafka offset组成事务。优先完成第33课的幂等数据库写入，再选择合适提交模式。记录每次重平衡和处理时长，避免只盯总吞吐忽略重复处理与长尾延迟。

一手阅读：Kafka Consumer 配置；Spring Kafka 消息监听容器。带着本课实验的输出阅读；有任何不清楚的步骤，可以直接把命令和结果发给学习助手继续追问。

重平衡测试应同时记录分区分配和消费者实例标识。一个组的消费者多于分区时，部分实例没有分区是正常现象；如果把它误判为故障反复重启，会造成更多重平衡。手动重置进度前先明确会重复执行哪些副作用，并确认幂等保留窗口仍覆盖重放范围。

已提交offset=12，恢复时通常从哪条位置开始？
查看判断依据

正确答案：恢复位置十二。提交值表示下一条要消费的位置，12代表此前位置已被视为处理完成。

把知识变成操作

观察同组消费者与新组消费者的区别。

  1. 用course-inspect组消费独立课程主题，稍候后描述group。
  2. 同组再启动第二实例，查看分区分配。
  3. 停止后以同group重启，观察已提交记录不会自动重放。
  4. 用新group加from-beginning读取，解释为何能重放保留期内记录。
验收信号

同组按分区分担工作；新组独立拥有进度；实际提交时刻会影响最后少量重放。
