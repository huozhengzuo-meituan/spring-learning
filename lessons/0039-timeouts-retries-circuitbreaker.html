Lesson 39 / 48 · 07 · 可靠性与运行时

超时、退避、熔断与隔离

为依赖调用分配时间与重试预算，避免局部故障变成全局拥塞。

约 30 分钟先修：第38课：负载与排队Java 21 · Boot 4.1
从你的前端经验出发

前端AbortController结束等待不保证服务器已停止执行；后端超时同样需要面对结果未知与副作用。

本课服务于同一个目标：独立交付并排查可靠的业务后端。实验入口：独立 jshell + 依赖故障策略设计。标注为教学片段或设计实验的代码需要按题目补入，不代表示例已实现该功能。

从整个请求的截止时间倒推

连接超时限制建立连接，响应或读取超时限制等待数据，总截止时间限制整个用户操作。一个接口预算1秒，不能给三个串行依赖各1秒并期待仍然1秒内返回。重试、退避和排队都占总预算。超时后对方可能已经提交订单或扣费，所以写操作重试必须带稳定幂等键并支持结果查询。取消客户端future未必能取消远程副作用，也未必释放底层任务占用的资源。

重试有乘法效应

调用链三层各最多尝试三次，最坏可能放大到27次末端调用；故障时这会进一步挤压下游。优先在知道业务语义的一层重试，仅针对可恢复错误，设置最大尝试与总时间，并使用指数退避加随机抖动。常规参数校验失败不重试，限流应尊重服务器可用的重试提示。下例是jshell预算演算，展示等待与执行时间必须一起计算；真实HTTP客户端还要正确配置连接池和底层超时。

int attempts = 3;
int perAttemptMs = 200;
int firstBackoffMs = 50;
int secondBackoffMs = 100;
int worstMs = attempts * perAttemptMs + firstBackoffMs + secondBackoffMs;
System.out.println(worstMs); // 750ms，不含排队及其他业务逻辑
System.out.println(Math.pow(3, 3)); // 三层嵌套重试最多27次末端尝试

熔断与隔离分别控制什么

熔断器根据一段窗口内的失败或慢调用表现决定是否暂时快速拒绝，并在半开状态少量探测恢复；它通常不自动限制并发，也不自己取消超时请求。Bulkhead隔离通过并发许可或有界线程池控制某个依赖最多占用多少资源，避免拖死所有请求。限流控制单位时间流量，三者不能混为一个开关。降级结果必须表达语义：无法查到最新任务状态时不能返回假成功，只能明确陈旧或暂不可用。

组合顺序需要实验

重试包在熔断器外或内，会改变熔断器统计的是每次尝试还是最终调用；是否把限流拒绝计为失败，也会改变行为。不要堆叠注解后不检查调用链。用隔离的假依赖依次返回超时、503、成功，观察尝试数、耗时、熔断状态与并发数，确认总预算没有被突破。恢复时也应缓慢放量，避免所有实例同时探测导致二次冲击。最后保存明确的依赖失败契约，而不仅是几段默认配置。

一手阅读：Resilience4j CircuitBreaker；Resilience4j Retry。遇到不明白的输出、时序或取舍，请把你的推理发给学习助手继续追问。

依赖恢复后还要观察积压释放过程。大量排队任务同时恢复可能再次打满下游，因此队列长度、超时任务清理和恢复放量同样属于设计。重试日志中记录尝试次数与最终结果，避免只看到最后成功而忽略为它消耗了过多资源。

合上笔记，先判断

熔断器之外，为保护连接池还应直接限制什么？
查看判断依据

正确答案：下游调用并发。熔断根据窗口状态拒绝调用；并发隔离限制正在消耗资源的调用数，两者作用不同。

把知识变成操作

为一个1秒预算的聚合API设计失败策略。

  1. 列出两个依赖的连接、请求、重试、退避预算。
  2. 只允许一层重试，写出允许重试的状态。
  3. 设置每个依赖的并发上限与队列上限。
  4. 模拟依赖提交成功但响应超时，说明用什么查询或幂等机制恢复。
验收信号
