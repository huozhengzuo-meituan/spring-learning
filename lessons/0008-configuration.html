配置、Profile 与密钥边界

预测配置覆盖结果，并避免将环境差异写进业务代码。

约 25 分钟先修：07Java 21 · Boot 4.1
从你的前端经验出发

前端构建变量常在打包时固化；后端可让同一构件在启动时接收不同环境配置。

本课服务于同一个目标：独立交付并排查可靠的业务后端。实验入口：examples/hello-api。标注为教学片段或设计实验的代码需要按题目补入，不代表示例已实现该功能。

同一构件，多种运行环境

端口、数据库地址、超时和功能开关不应该散落在业务代码里。Boot 支持 properties、YAML、环境变量和命令行参数等配置来源。常用场景下，命令行可以覆盖环境变量，环境变量可以覆盖打包配置；测试注解等还有更高优先级来源，因此完整排查必须看实际来源而非记住一句“环境变量最大”。

Profile 是按环境或运行模式选择配置集合的机制，不是隔离安全域的万能工具。本项目 task-service 的默认模式使用本地 H2，postgres 模式使用 PostgreSQL，infra 模式再启用 Redis/Kafka。开启 profile 本身不会帮你启动外部服务，依赖不可达时仍需按连接错误处理。

原始资料：Spring Boot 外部配置。

通过端口实验理解覆盖

先保持源码中的默认端口不变，用环境变量启动为 8181，再同时传入命令行 8282，观察最终监听地址。预期由命令行获胜。配置对错应通过日志和真实端口访问验证，而不是只看文件内容。若项目已有进程，先正常停止，避免把旧进程响应误认为新配置生效。

结构化业务配置优先使用 @ConfigurationProperties 绑定到有明确类型的对象，再结合校验及时拒绝负数超时或空地址。不要把所有配置都读成字符串后到处手动解析。零散 @Value 可用于小范围值，但成组配置需要可发现的前缀、默认值和边界条件。

SERVER_PORT=8181 ./mvnw -f examples/hello-api/pom.xml spring-boot:run \
  -Dspring-boot.run.arguments=--server.port=8282
# 在另一终端；预期只在最终选定端口成功
curl -i http://localhost:8282/api/tasks
# 停止后正常启动，恢复源码配置
./mvnw -f examples/hello-api/pom.xml spring-boot:run

原始资料：Spring Boot Profiles。

配置也需要变更和安全管理

密钥不能提交进 Git，示例账号和本地容器密码只服务学习环境。部署时由受控秘密管理机制注入，并限制日志、诊断端点和进程信息暴露。把密钥写到一个名为 application-prod.properties 的文件，不会因为名称含 prod 就变安全；把文件加入 gitignore 也无法抹掉它曾经进入历史的事实。

配置变化应有审查、回滚和观测。例如将连接池增大十倍可能耗尽数据库连接，不是单纯“更快”。属性拼错时可能静默不生效，所以要检查绑定对象和运行结果。完成练习后在记录中写清来源、预期值、实际值，逐渐建立“配置是系统行为的一部分”的意识。

原始资料：Spring Boot Profiles。

合上笔记，先判断

本课同时设置环境端口和命令行端口，谁优先？
查看判断依据

正确答案：命令行的配置。在本课普通启动条件下，命令行属性覆盖环境变量与文件配置；测试等特殊来源需另查完整优先级。

把知识变成操作

验证端口覆盖并还原运行环境。

  1. 停止旧 hello-api，执行同时包含8181和8282的启动命令。
  2. 请求8282，观察启动日志；确认8181没有这次服务监听。
  3. Ctrl+C后使用普通命令重启，确认8081恢复。
验收信号

临时启动为8282，普通启动恢复8081，源码不需要修改。

做完再看：参考答案与排错线索

SERVER_PORT 是环境变量映射；--server.port 是Boot命令行属性。本次优先级为命令行8282 > 环境变量8181 > 文件8081。不要把 shell 的赋值误写为永久修改系统环境。
